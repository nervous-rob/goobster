# Development Standards and Project Goals

## Project Overview
Goobster is a self-hostable Discord bot designed to provide engaging AI chat, helpful utilities, music playback, and fun features for users. This edition is optimized to run on low-power hardware such as a **Raspberry Pi 4B**, with no mandatory cloud dependencies.

## Architecture Principles

### Self-hosted first
- **Local SQLite database** (better-sqlite3, WAL mode) — no external database server. All schema lives in `db/schema.sql` and is applied automatically when the database opens.
- **Local file storage** for music (`data/music`), playlists (`data/playlists`), and images (`data/images`) — no cloud blob storage.
- **System FFmpeg** for all audio work (multi-arch, including ARM64) — never binary-only npm packages that ship a single architecture.
- **Graceful degradation**: every cloud integration (OpenAI, Anthropic, Gemini, Perplexity, ElevenLabs, Spotify) is optional. Missing credentials must produce a warning and disable the feature — never a startup crash.

### Database access
- All database access goes through the `db/` module: `db.get(sql, params)`, `db.all(sql, params)`, `db.run(sql, params)`, and `db.transaction(fn)`.
- SQL is written natively for SQLite (UPSERT via `ON CONFLICT`, `LIMIT`, `datetime('now', ...)`, `CURRENT_TIMESTAMP`, `RETURNING`).
- Named parameters use the `@name` style. Values are normalized automatically (booleans → 0/1, Date → UTC text, objects → JSON).
- Discord snowflake IDs are stored as **TEXT** (they exceed JavaScript's safe integer range).
- Timestamps are stored as UTC text (`YYYY-MM-DD HH:MM:SS`).

### AI providers
- `services/aiService.js` routes between providers: **OpenAI** (default when configured), **Anthropic** (Claude), **Gemini**, and **Ollama** (local LLM, used automatically as fallback when no cloud provider is configured). Auto-detect order: OpenAI → Anthropic → Gemini → Ollama.
- **Full parity across the three cloud providers**: each has a `chatModel` (everyday tier) and a `thoughtfulModel` (state-of-the-art tier), native tool calling, text streaming, native web search, vision, and `opts.reasoning_effort` support. Feature work must preserve this parity — never add a capability to one cloud provider without the others.
- All model IDs and API keys are resolved through `config/aiConfig.js` (environment first, then `config.json`, then defaults). Never hardcode a model ID in a service or command.
  - Chat defaults (latest model of each platform's standard tier): OpenAI `gpt-5.6-terra`, Anthropic `claude-sonnet-5`, Gemini `gemini-3.5-flash`.
  - Thoughtful defaults (used with high reasoning effort): OpenAI `gpt-5.6-sol`, Anthropic `claude-fable-5`, Gemini `gemini-3.1-pro-preview`.
  - Other defaults: images `gpt-image-2`, Perplexity `sonar-pro`.
- Provider contract — every provider implements:
  - `chat(messages, opts)` → `{ content: string, toolCalls: [{ id, name, arguments }] }` (never a raw SDK response).
  - `generateText(prompt, opts)` → `string`.
  - `isConfigured()`, `setDefaultModel(name)`, `getDefaultModel()`.
  - Accepted message roles: `system`, `user`, `assistant` (optionally carrying `toolCalls`), and tool results as `{ role: 'tool', toolCallId, name, content }`.
  - `opts.onDelta(textDelta)` enables streaming; providers invoke it per text chunk and still return the full normalized result.
  - `opts.reasoning_effort` (`minimal`/`low`/`medium`/`high`) maps to each provider's reasoning knob: OpenAI `reasoning.effort`, Anthropic `output_config.effort` (`minimal`→`low`; skipped on models without effort support, e.g. Haiku), Gemini `thinkingConfig.thinkingLevel` (Gemini 3.x only; `minimal`→`low` on Pro models). Unsupported combinations are silently dropped, never errors.
  - **Token budgeting**: callers size `opts.max_tokens` for the *visible* reply only. Hidden reasoning shares the same output cap on all three platforms (OpenAI reasoning tokens, Claude thinking, Gemini thinking), so providers add a thinking allowance on top via `utils/aiTokenBudget.js` (`withThinkingHeadroom`: minimal +1k, low +4k, medium +8k, high +24k) whenever reasoning is active — including model defaults when no effort is requested (OpenAI reasoning models default `medium`, Claude adaptive-thinking models `high`, Gemini 3.x Flash `medium`/Pro `high`). Never hand-tune inflated `max_tokens` at call sites to make room for thinking. The model's native hidden thinking channel *is* the per-reply scratchpad; don't build prompt-level scratchpad loops for cloud providers.
- OpenAI uses the **Responses API** (`client.responses.create`) — not Chat Completions or the legacy `functions` parameter. Reasoning models (GPT-5 family, o-series) must not receive `temperature`/`top_p`; use `reasoning: { effort }`.
- Anthropic uses the **Messages API** via plain `fetch` (no SDK dependency). Adaptive-thinking models (Claude Fable/Mythos 5) and effortful requests must not receive `temperature`/`top_p`; on newer Claude models the two are mutually exclusive, so the provider sends only one.
- Thoughtful Mode is provider-aware: `aiService.getThoughtfulPreset(providerKey)` returns `{ provider, model, reasoningEffort: 'high' }` using the provider's `thoughtfulModel` (null for Ollama). `/thoughtfulmode` and the panel toggle pin the preset for the guild's effective provider.
- Tool calling: OpenAI, Anthropic, and Gemini use native function calling; Ollama uses the prompt-based JSON protocol from `utils/toolPromptBuilder.js`. Shared tool guidance lives in that module — never duplicate tool prompts inside a provider.
- **Agent orchestration** (`utils/chat/agentOrchestrator.js`, see `documentation/agent_orchestration.md`): text-chat turns run tool calls through `runAgentLoop`, a bounded LangChain-AgentExecutor-style loop over the provider contract — up to 6 sequential tool rounds (each step sees prior results), duplicate-call caching, tool errors fed back as recoverable observations, and a **guaranteed user-facing answer**: a finalization nudge when the round budget runs out, then a transcript digest as the last resort. Never reintroduce an inline tool loop that can exit without producing reply text. Tool transcripts persist in `messages.metadata` and recent ones are re-injected into the next turns' system prompt (`PRIOR TOOL RESULTS`) via `chatDb.getRecentToolTranscripts` + `buildPriorToolContext`, so follow-ups can use already-fetched data. LangChain-the-dependency was evaluated and rejected (it would replace the provider router and its per-guild overrides/usage tracking, and is too heavy for the Pi target) — extend the orchestrator instead.
- Web search: OpenAI (`web_search` built-in tool), Anthropic (`web_search` server tool), and Gemini (Search Grounding) search natively mid-response via `opts.webSearch`; the legacy detect-and-approve Perplexity flow only runs for providers without native search (Ollama). Perplexity remains the backend for the `performSearch` tool and `/search` command.
- Image generation goes through `openaiService.generateImage()`/`editImage()` (GPT Image models return base64, not URLs). DALL-E models were removed from the OpenAI API in May 2026.

### Long-term memory
- `services/memoryService.js` stores message embeddings in the `memory_embeddings` SQLite table and recalls them by cosine similarity (`services/embeddingService.js`: OpenAI `text-embedding-3-small`, or Ollama `nomic-embed-text` when self-hosted).
- Recall is indexed: vectors are mirrored into per-dimension `vec0` virtual tables (`memory_vec_<dims>`, partitioned by `guildId|model`, cosine distance) via the **sqlite-vec** extension, loaded in `db/index.js` (prebuilts cover x64 and ARM64 incl. Pi 4B). When the extension can't load, recall transparently falls back to the original brute-force scan. Every deletion path (prune, retention, channel exclusion, per-user/guild erasure, `/forget-me`) must clean orphaned vectors — derived embeddings never outlive their memories. First use backfills pre-index rows (`syncVecIndex`).
- Memory writes are fire-and-forget (never block or fail a reply); recall injects a `LONG-TERM MEMORY` block into the system prompt, excluding content already in the active context window.
- Vectors are only compared when produced by the same embedding model; per-guild storage is capped (default 5000 entries) and admins can inspect/clear via `/memory`.
- `/recall <question>` exposes memory directly ("ask the server anything"): retrieves relevant memories, filters out ones from channels the asking user cannot view, and synthesizes a grounded answer with source snippets. Invocations are counted in `command_log` (via `usageTracker.logCommand`) and surfaced in `/usage`.

### When Goobster answers in a guild channel
- `events/messageCreate.js` is the only gate, and its order matters: agent mission-control threads → reply-to-edit on his images → **explicit address** → **reply detection** → the opt-in dynamic-response score (`utils/intentDetectionHandler.js`, `/dynamicresponse`, default off).
- An **explicit address** is an @mention, a role-style `<@&botId>` mention, his username or guild nickname in the text, **or a Discord reply to one of his messages**. The reply ping is a per-user toggle, so the mention list can't be relied on to spot a reply — resolve the referenced message instead.
- **Reply detection** (`utils/replyDetection.js`, `guild_settings.reply_detection`, default ENABLED, `/replydetection`): every guild message joins a short in-memory per-channel tail, his own included, because those are the ones that arm the detector. When a user's message directly follows one of his, a cheap deterministic model call reads the exchange and answers `reply` or `unrelated`; only a reply gets a response. The trigger is **positional, not timed** — a message he sent long ago still counts when somebody picks the thread back up, and the gap is handed to the classifier as context rather than enforced as a cutoff.
- Guardrails on that model call: messages visibly aimed elsewhere (another member mentioned, `@everyone`/role ping, a reply to a human, another bot's command prefix) are rejected before it happens, and the positional rule bounds cost to **at most one classification per message Goobster sends** — once a human message lands, the channel's last message is no longer his. A classifier failure degrades to recency (90s), and a channel with no remembered tail (fresh process) fetches its previous message from Discord once. The tail is transient, re-derivable state, so it stays in memory rather than SQLite.

### Direct messages (one-on-one conversations)
- Goobster works in DMs: every human DM is an **implicit prompt** (no mention or `/chat` needed) — `events/messageCreate.js` routes DMs to the same chat pipeline used for mentions. Reply-to-edit for images works in DMs; reactions work except 🌱 branching (DMs have no threads, it politely declines).
- **DM scope rule**: everything keyed on `guildId` (chat rows in `guild_conversations`, `memory_embeddings`, `facts`, usage attribution) uses the synthetic per-user scope `dm:<userId>` from `utils/dmScope.js` (`dmScopeId`, `getConversationScopeId`) in DMs. This satisfies the NOT NULL guild columns, isolates each user's DM data from guilds and from other users, and lets memory recall/facts/consolidation work unchanged. Never store DM data under a NULL or shared guild id.
- **Command availability**: command modules flagged `dmAllowed: true` are registered **once globally** with DM interaction contexts (GUILD, BOT_DM, PRIVATE_CHANNEL) by `deploy-commands.js`; all other commands stay guild-registered so they never appear in DMs. A command must never be in both sets (it would show up twice in guilds). `index.js` also refuses guild-only commands invoked from a DM (defense-in-depth). DM-flagged commands must be null-guild safe. The global bulk update always carries through any existing `PRIMARY_ENTRY_POINT` command (type 4, the Activity "Launch" command) - Discord rejects bulk updates that would remove it (error 50240). Payload assembly lives in `utils/commandDeployment.js` (shared by the deploy script, `tests/globalCommandPayload.test.js`, and `scripts/verify-global-commands.js`, which reads back what Discord has registered and, with `--put`, attempts the bulk overwrite with loud 400-vs-rate-limit reporting).
- **DM admin rule**: a DM is treated like a one-member guild whose member is the admin. Settings commands flagged for DMs (`/personalitydirective`, `/aisettings`, `/thoughtfulmode`, `/nickname`) store their values in `guild_settings`/`user_nicknames` under the DM scope, skip guild permission checks in DMs (there is nobody else to protect), and the chat pipeline resolves them per scope (`getGuildAI`, `getPersonalityDirective`, and the name helpers all take the conversation scope id). Prompt wording is scope-aware (`DM DIRECTIVE` vs `GUILD DIRECTIVE`).
- Other guild-only features stay guild-only in DMs: heartbeat mood, internal monologue, activity counters, economy, voice, and music. DM memory has no retention window (no retention set on the DM's `guild_settings` row by default) but is capped like a guild (`maxEntriesPerGuild`).
- **Voice cannot work in DMs**: Discord's API does not let bots join DM/group-DM calls (voice connections are guild-scoped; `joinVoiceChannel` requires a guild adapter). Do not attempt to add DM voice - point users at a guild voice channel instead.
- Privacy: `/what-do-you-know-about-me` reports the user's DM scope when run in a DM; `/forget-me` works from DMs and erases DM-scoped memories (both sides), DM facts, and DM conversation containers/summaries (audited by `privacyService.auditUser`).

### Privacy controls (product features, not just positioning)
- `/what-do-you-know-about-me` — per-user transparency report (ephemeral): facts, memory counts, pending follow-ups, nickname, preferences, chat-history totals, usage rows, activity counters. Built by `services/privacyService.js` `buildUserReport`.
- `/forget-me` — full per-user erasure (button-confirmed, bot-wide, single transaction) via `privacyService.forgetUser`:
  - **Deletes:** `memory_embeddings` by `authorId` plus everything in the user's DM scope (`dm:<userId>`), USER-subject `facts` plus all DM-scope facts, `followups` created by the user, the user's conversation history (`messages`, `conversations`, `prompts`, DM conversation containers and summaries), `user_nicknames`, `UserPreferences`, and the `users` row.
  - **Anonymizes:** `usage_log`/`command_log` rows (userId nulled, token counts kept for cost accounting) and `guild_activity` rows (userId nulled, message counts kept so server-wide `/wrapped` totals stay accurate).
  - **Review pass:** GUILD-subject `facts`, `conversation_summaries`, and follow-up notes are scanned for the user's known names (username, display names, stored nicknames, memory author names) with word-boundary matching, and matches are deleted. Never skip this pass.
  - `privacyService.auditUser` re-counts user-attributed rows afterwards; the command reports the audit so "zero gaps" is provable.
- `/privacy` (Manage Server) — retention and scope: `retention days:<n>` sets `guild_settings.memory_retention_days` (purged on write and nightly from the consolidation run via `memoryService.applyRetentionAll`); `exclude`/`include channel:<c>` manage `memory_channel_exclusions` (excluding also purges that channel's stored memories **and its `guild_activity` counter rows**; `memoryService.remember` and `activityService.recordMessage` both refuse excluded channels).

### Activity counters and Server Wrapped
- `services/activityService.js` counts messages into the `guild_activity` table (one aggregated row per guild/channel/user/UTC-day, UPSERT increment) from the `messageCreate` event. **Counts only — message content is never stored.** Recording is wrapped like `usageTracker.log`: it must never break message handling. Channels excluded via `/privacy` are skipped, and `/forget-me` anonymizes a user's rows (userId nulled, counts kept — NULLs are distinct in SQLite unique indexes, so anonymization cannot hit a PK conflict and aggregations simply SUM across rows).
- `services/wrappedService.js` aggregates Server Wrapped stats per guild and window (activity totals/top members/top channels/busiest day from `guild_activity`; AI calls and tokens from `usage_log`; command and `/recall` counts from `command_log`; new memories, facts, and delivered follow-ups from the memory tables). `resolvePeriod` maps `this-month`/`last-month`/`this-year` to UTC date windows. `buildBlurb` optionally adds a short AI-written intro (never throws; returns null without a provider).
- `/wrapped show [period]` (`commands/utility/wrapped.js`) posts the recap **publicly** — it's a shareable artifact. Presentation lives in `utils/serverWrapped.js` (`buildWrappedMessage`): an embed is always rendered; when OpenAI is configured, a stats-card image is generated via `openaiService.generateImage()` (model resolved through `config/aiConfig.js`) and attached, falling back to embed-only on any failure. Invocations are logged to `command_log`.
- `/wrapped schedule|unschedule` (Manage Guild) manages a monthly `automations` row with promptText marker `__SERVER_WRAPPED__` (cron `0 17 1 * *`), handled directly by `automationService.executeWrapped` — like `__CHANNEL_DIGEST__`, it bypasses the chat pipeline and the user-online check, and wraps the month that just ended.

### Usage tracking, vision, per-guild AI, and digests
- `services/usageTracker.js` logs token counts for every AI call (`usage_log` table); providers report usage automatically (including streaming and Ollama), with attribution threaded via `opts.usageContext = { guildId, userId }`. `/usage` shows per-guild summaries.
- Vision: user messages may carry `images: [url]`; OpenAI passes URLs directly, Gemini/Ollama download and inline base64. Sources: image attachments on mentions and the `/chat` `image` option.
- Per-guild AI overrides (`/aisettings`, `/thoughtfulmode`): `guild_settings.ai_provider/ai_model/ai_reasoning_effort` are applied per-request via `opts.provider`/`opts.model` — never by mutating global provider state.
- Reply-to-edit: replying to a bot message containing an image routes to `imageDetectionHandler.editImageFromUrl()` (gpt-image-2 edits endpoint).
- `/digest now|schedule`: channel summaries via `utils/channelDigest.js`; scheduled digests are `automations` rows with promptText `__CHANNEL_DIGEST__` handled specially by `automationService`.
- Generic `/automation` prompts are unattended agent turns: when due, `automationService` supplies the owning user/member plus the guild and channel to the normal `handleChatInteraction` pipeline regardless of the owner's presence. The same full tool registry and bounded multi-round agent loop used by text chat decides whether to answer, search, or perform one or more actions, so scheduled tasks can use economy, stock, gambling, and future registered tools without a second command parser. Existing tool guardrails still apply (for example, Cursor launches and GitHub issue creation remain confirmation-gated).
- **Automation runs are claimed before they execute** (`automationService.claimDueRun`): an atomic UPDATE advances `nextRun` while the row is still enabled and due, so each scheduled fire runs at most once — a restart or a replayed due list mid-execution never double-runs it, and a failed run waits for its next scheduled fire instead of retrying every poll. `lastRun` is set only after a successful run. Never move `nextRun` advancement back to after execution. **All cron evaluation is UTC** (`{ tz: 'UTC' }` at every `CronExpressionParser.parse` that computes `nextRun` — the claim, both manager services, and the built-in wheel/wrapped/digest schedules), matching the UTC contract the tool descriptions document; never parse a schedule in the server's local timezone. A row whose cron no longer parses is **disabled** (instead of being rescanned every minute forever) with a best-effort notice to its channel; a run that throws notifies the owner's channel **once per failure streak** (`metadata.failureNotified`, cleared by the next success) so a broken automation is never silent — and never spammy. The poll loop waits at most `executionWaitMs` (15 min) on one run before moving on — a straggler keeps running in the background and can't be re-claimed, so one wedged turn can't starve every other automation.
- **Automation turns are a trusted surface for web-scoped tools** (`isAutomation` on the pseudo-interaction → `toolsRegistry.getDefinitions` + the `runCode`/`observatory` execute gates): the prompt was authored through an already-gated surface, so its unattended runs get the same tool set — otherwise an automation created in the web app to drive an Observatory project could never touch it. The inverse rule also holds: **an automation run may never `create` another automation** (`manageAutomations` refuses on `isAutomation` turns) — a prompt phrased "check X every hour" would otherwise spawn a sibling on every fire until the per-scope cap, a runaway multiplication of unattended model calls.
- **The assistant routes recurring work to automations** via the `manageAutomations` tool (`utils/toolsRegistry.js` → `services/automationManagerService.js`): create/list/pause/resume/cancel by name, scoped to the conversation (guild channel → guild automation posting there; Discord DMs and the web portal → DM-scope rows delivered to the user's Discord DM channel, the portal Tasks-pane rules). Validation (5-part cron, 15-minute minimum gap, 10-per-scope cap, duplicate names) lives in `automationManagerService`; `webTaskService` reuses the same `validateCron` so every creation surface enforces identical guardrails. Any request for recurring/repeating work ("every hour", "daily at 9am") must become an automation — never a chain of one-time follow-ups (the routing rule is stated in the tool descriptions and in `toolPromptBuilder`'s shared scheduling guidance).

### Facts, follow-ups, and the heartbeat (proactive mode)
- `services/factsService.js` stores distilled facts (`facts` table) about users and the server - separate from raw embeddings. The model curates them itself via the `rememberFact`/`forgetFact` tools; per-user dossiers and server facts are injected into every chat prompt.
- `services/memoryConsolidationService.js` runs daily ("sleep cycle"): reviews the last day's raw memories per guild and distills new durable facts, deduplicated against existing ones.
- `services/followupService.js` (`followups` table) holds self-scheduled follow-up **reminders** created by the `scheduleFollowUp` tool; delivery runs every minute from the heartbeat. A follow-up is **one-shot by default** (PENDING → DONE on delivery) or a **recurring reminder** via the tool's optional `repeat` parameter ("every hour", "daily" — parsed deterministically in `parseRecurrence`, no model call; floor 15 minutes to match the automation cron guardrail, ceiling one year). Recurring rows carry `recurMinutes` + a human `recurrence` label and **stay PENDING**: each successful delivery atomically advances `dueAt` to the next occurrence strictly in the future (`recordDelivery`, guarded on status AND the exact dueAt being delivered so a duplicate pass is a no-op), skipping occurrences missed while the bot was down — a restart yields one catch-up delivery, never a burst. Delivery order is send-then-record (a failed send stays PENDING at the same dueAt and retries next minute), and `deliverDueFollowups` holds a re-entrancy guard so a slow model call can't overlap the next tick and double-deliver. Cancellation ends the whole series through the existing PENDING-gated paths (portal Tasks pane `cancelFollowup`, `followupService.cancel`).
- **The follow-up/automation boundary**: follow-ups are *reminders* — a delivery only phrases the stored note, never runs tools. Recurring **work** (anything that must check, fetch, generate, or act on each run) belongs to durable automations (`manageAutomations` / `/automation` / portal Tasks), which execute full unattended agent turns. Recurrence must never be simulated by chaining one-shot follow-ups; the routing rule is stated in both tool descriptions and `toolPromptBuilder`'s shared scheduling guidance.
- `services/heartbeatService.js` is the proactive agent tick (every 20 minutes): for guilds opted in via `/proactive`, it reviews the most active channel, known facts, and pending follow-ups, then decides via a cheap model call to chime in, react, update its mood, or (the default) stay silent. Guardrails: opt-in per guild, 45-minute action cooldown, minimum-activity bar, and no interrupting when the bot spoke recently. The per-guild mood it maintains subtly colors normal chat replies.
- Heartbeat state (mood + cooldown anchor) persists in the `heartbeat_state` table so restarts don't reset cooldowns or forget the server vibe.
- Schema note: `db/index.js` has a minimal column-migration helper (`applyColumnMigrations`) because `schema.sql` only creates missing tables; new columns on existing tables must be added there.

### Internal monologue and knowledge graph
- `services/monologueService.js` is a background thought process, opt-in per guild via `/monologue` (`guild_settings.monologue_mode`). Every tick (15 minutes, 30-minute per-guild cooldown) it privately reviews the most active channel's recent conversation, its own scratch pad, recalled long-term memories (`memoryService.recall`), known facts, and a relevant knowledge-graph excerpt, then answers with ONLY JSON: a required `thought` (journaled to `monologue_thoughts`), optional `scratchpad` add/remove operations (`monologue_scratchpad`), and optional `graph` mutations (node upsert/link/delete). **Nothing here posts to Discord** - the monologue is introspection only.
- The cooldown anchor is derived from `monologue_thoughts.createdAt` (restart-safe, per the SQLite-not-memory rule). Ticks are skipped when the guild is quiet (fewer than 2 human messages in 2 hours, or nothing new since the last thought), and channels excluded via `/privacy` are never observed. Per-tick action caps bound how much one model response can change (4 note adds, 6 node upserts, 10 links, 3 node deletes).
- `services/knowledgeGraphService.js` owns the per-guild semantic network: `kg_nodes` (types: concept/fact/opinion/experience/person/place/event/thing, labels unique per guild case-insensitive, salience 0-1) and `kg_edges` (typed, weighted semantic relationships; `ON DELETE CASCADE` from either endpoint). It exposes create/update (`upsertNode` - omitted fields are preserved), query (`searchNodes` keyword match, `topNodes`, `getNeighborhood` BFS traversal), delete, `link`/`unlink` (missing endpoints are auto-created as stub concepts), and prompt rendering (`describeForPrompt`). Storage is capped (500 nodes / 1500 edges per guild), pruning the least salient, least recently touched first.
- Chat integration: when the mode is enabled, the chat pipeline injects a compact `INNER LIFE` block (latest private thought, a few scratch pad notes, knowledge-graph nodes relevant to the incoming message) into the system prompt via `monologueService.buildChatContext` - the prompt explicitly forbids quoting or revealing it.
- `/monologue` (Manage Server): `enable`/`disable`, `status` (counts), `thoughts` (peek at recent private thoughts + scratch pad, ephemeral), `graph` (most salient nodes and links, ephemeral), `reset` (erase thoughts, scratch pad, and graph). The panel Settings tab mirrors the toggle (`monologueMode`).
- Privacy: `/forget-me` runs review passes over `monologue_thoughts`, `monologue_scratchpad`, and `kg_nodes` (label + content) with the same word-boundary name matching as guild facts; matching rows are deleted and incident edges cascade.

### Point economy, gambling, and the stock trading game
- `services/economyService.js` owns the per-guild point currency: `economy_settings` (currency name — anything, e.g. "Jimmy points" — plus starting balance and daily amount), `economy_wallets` (INTEGER balances, never negative, enforced in code and by CHECK constraint), and `economy_transactions` (a full ledger: signed amount + resulting balance per change). **Every point movement goes through `economyService.adjust()`** — games, trades, grants, daily claims — so the ledger is complete by construction. Wallets are created lazily with the guild's starting balance (recorded as a `starting-balance` ledger entry). Errors use `EconomyError` (machine-readable `code` + user-presentable `message`); commands and tools surface the message directly.
- `/points` (`commands/economy/points.js`): balance, `daily` (24h cooldown tracked in SQLite), `give` (atomic transfer), leaderboard, `history` (ephemeral ledger view); `admin` subcommand group (Manage Server) renames the currency and sets starting/daily amounts (`/points admin name|grant|config`).
- `services/gamblingService.js` + `utils/pokerHands.js` implement the games behind `/gamble`: coin flip (call heads/tails), d20 showdown (both roll, higher wins, tie pushes), and 5-card poker vs. the dealer (one shuffled deck, standard hand rankings incl. the wheel, kicker tie-breaks). All games pay even money and settle as a **single net ledger entry** (`gamble-<game>` with a JSON detail of the outcome). The RNG is constructor-injectable (`new GamblingService(rng)`) so game logic is deterministic under test; bets are validated against the balance before any dice are rolled.
- `services/stockService.js` is the market data layer for the stock game: quotes and daily history from Yahoo Finance's keyless public endpoints (chart + search), with a **short-TTL quote cache in SQLite** — every fresh fetch upserts `stock_symbols` (the symbol indicator database, grown by lookups/searches) and appends a `stock_prices` snapshot; quotes younger than 5 minutes are served locally, and on network failure the last snapshot of any age is returned flagged `stale` (graceful degradation, no API key required). Errors use `StockError`.
- `services/stockPortfolioService.js` is the trading game: **1 point = $1**, `units` are shares (fractional to 4 dp). `buy` debits `ceil(units × price)` points, `sell` credits `floor(units × price)` (rounding always favors the house); holdings keep an average cost basis (`stock_holdings`), every fill is recorded in `stock_trades` (side, units, price at trade time, points moved), and `getPortfolio` re-quotes each symbol to compute value and P/L vs. cost. Only USD-quoted symbols are tradable (the peg would otherwise need FX). `/stocks` exposes quote, search, buy, sell, portfolio (works for other users too), `chart` (historical price graph rendered as SVG → PNG via sharp in `utils/stockChart.js`, unicode-sparkline fallback), and `trades`.
- Chat/voice integration: `toolsRegistry` exposes `checkPoints`, `gamblePoints`, `stockQuote`, `tradeStock`, and `checkPortfolio`, all included in the voice session tool subset — the whole economy is operable by speaking to the bot.

### The Jimbucks Exchange (margin, shorts, options, orders, event contracts)
Full guide: `documentation/jimbucks_exchange.md`. Services live under `services/exchange/`.
- **The invariant that outranks every feature here: all point movement still goes through `economyService.adjust()`, and a wallet is never negative.** What the exchange adds are *liabilities* held beside the wallet — `exchange_accounts.marginLoan` (points owed), `short_positions` (units owed) — so `equity = cash + longs + options − shorts − debt` and the ledger still explains every point in every wallet. Errors use `ExchangeError` (`services/exchange/errors.js`), same code+message contract as `EconomyError`/`StockError`.
- **Everything risky is off per guild until an admin turns it on** (`exchangeConfig`, `exchange_settings`; `/exchange settings`). A server that never opts in keeps the plain cash stock game, and the cash path through `stockPortfolioService.buy` is unchanged (it only consults `accountService` when the account is MARGIN).
- **Pure math is separated from I/O and is the tested core**: `optionsMath.js` (Black-Scholes price/greeks/implied vol/probabilities/realized vol) and `marginMath.js` (equity, maintenance, buying power, per-position liquidation price, market-move-to-margin-call, liquidation planning). Every number shown to a trader *before* they take leverage comes from these, so it is testable in isolation. Never inline this math into a service.
- **Option premiums are simulated and must always say so.** No keyless real chain exists (Yahoo's options endpoint requires an authenticated crumb), so `optionsMarket` prices contracts with Black-Scholes on the **real** underlying: volatility from three months of real daily closes (cached in `stock_symbols.impliedVol`/`ivUpdatedAt`, added via `applyColumnMigrations`), plus a front-week term bump and a house spread - deliberately ONE vol per expiry, no per-strike smile: a smile can invert strike ordering (a higher call strike pricing above a lower one), a vertical arbitrage once writing exists. Index aliases (`SPX`→`^GSPC`, `NDX`, `RUT`, `VIX`, `DJX`/`DJI`) make spoken tickers work; all contracts are cash-settled at 20:00 UTC on the expiry date.
- **Long options are cash-paid; written options are margin-backed.** Buying a contract has a known maximum loss (the premium), paid in **cash and never borrowed** — long options are not marginable collateral, so they add to equity but are excluded from the buying-power base and create no maintenance requirement. **Writing** (`sellToOpen`) needs a MARGIN account, collects the bid premium, and consumes a requirement enforced against buying power before the fill: the naked 20% rule (`marginMath.nakedShortRequirement`), the strike width when paired into a spread, and zero when a call is covered by shares (`marginMath.optionBookRequirement`, greedy nearest-strike pairing — longs and shares consumed as cover are never reused). At settlement an assigned writer pays the intrinsic ceiling, borrowed onto the margin loan when the wallet cannot (`option-assign`); one user can never hold and have written the same contract (the reconcile invariant `long-and-short-contract` enforces it).
- **Multi-leg spreads follow the receipt-then-fire contract** (`spreadService`, `/options spread`, `tradeSpread` tool): `quote()` builds the full pre-trade receipt (every leg's debit/credit, net, max gain/loss, break-evens, collateral, simulated-pricing timestamp, 0DTE warning) and `execute()` only runs after that — debit legs before credit legs so written wings land on their cover, and any failed leg unwinds the filled ones at the same cached quotes (`SPREAD_FAILED`): a spread never half-exists. Payoff analysis is `spreadMath.analyzeSpread` (exact piecewise-linear: vertex profits + the call slope beyond the top strike), honest about unbounded sides; structure names come from `classifySpread` and anything unrecognized is called a custom spread.
- **Perpetual futures are isolated-margin, deliberately** (`perpsService`, `/futures`, `tradePerp`; `futuresEnabled` off by default, `maxPerpLeverage` cap): the posted margin leaves the wallet at open and IS the maximum loss, funding rent (`fundingRateDaily` × notional) erodes it on the engine tick, and liquidation fires when the mark crosses `marginMath.perpState`'s liquidation price (20% maintenance buffer returned as the remnant). Perp value counts in equity but never as collateral — a perp cannot back a stock loan and a stock cannot bail out a perp — which is also why perps are allowed on cash accounts.
- **Corporate actions are real and applied exactly once** (`corporateActionsService`, engine tick, throttled ~daily per symbol): dividends and splits come from the same keyless chart endpoint (`events=div,splits`). Longs are paid the floor, shorts owe the ceiling (borrowed onto the loan when needed); splits adjust stock/short units, option strikes/premiums (whole ratios multiply contracts, the OCC way), resting-order prices, event-contract thresholds, and perp entries — total cost bases unchanged, value conserved. Events seen on a symbol's FIRST sweep are recorded in `corporate_actions` WITHOUT being applied: back-paying history to positions that did not exist would invent money. Never violate that rule.
- **Group play runs on the opt-in registry** (`groupPlayService`, `exchange_optins`): precedence is (1) an explicit per-user record ALWAYS wins — an opt-out is honoured even while the override is on; (2) otherwise the guild's `optInOverride` decides (**ON by default**: every wallet holder is in); (3) override off means explicit opt-ins only. Per-user `maxAllocationPercent` caps what one event may deploy. Every consent change is an `exchange_events` row. The **Ballistic Goblin Wheel** (`wheelService`, `/wheel`, `goblinWheel` tool, `__GOBLIN_WHEEL__` automation for the weekday 13:30 UTC dedication) is the consumer: injectable RNG (deterministic under test), the published odds (strike wheel 80/19/1, allocation wheel 50/30/15/4/1), nearest listed strike at spot×(1+target%), and per-participant deployment where being skipped for poverty is a reported reason, never an error. Participating stands in for the personal Goblin Mode flag on the same-day leg (`viaGroupEvent`, set only by trusted server code and never exposed to a command or tool); the flag itself is never silently flipped. Spinning by tool requires Manage Server AND `confirm: true`.
- **0DTE needs two deliberate switches**: the guild's `zeroDteEnabled` AND the trader's own Goblin Mode (`exchange_accounts.goblinMode`, `/margin goblin`). The opt-in is recorded in `exchange_events`, and every same-day purchase still shows max loss, break-even, and the odds. Keep both gates on any future same-day instrument.
- **`services/exchange/riskEngine.js` is the only component that acts unprompted** (5-minute tick, started/stopped in `index.js` as `client.exchangeRiskEngine`, timer unref'd). Per guild, in order: accrue interest and borrow fees → settle expired contracts → settle due event markets → evaluate resting orders → mark accounts, raise margin calls, force-liquidate past the grace period (immediately at zero equity). **A snapshot with any unpriced position never liquidates and never settles** — a feed outage must defer, never guess. Notifications are best-effort DMs; the event log is the durable record.
- **Two records, deliberately**: `economy_transactions` says *what* moved, `exchange_events` (`exchangeEvents.record`, wrapped like `usageTracker.log` so auditing never breaks the action) says *why*. Every automatic action and every risk opt-in lands there, so a liquidation is explainable after the fact.
- `services/exchange/auditService.js` is **read-only by construction**: `auditAccount` (positions, live greeks, leverage, liquidation levels, realized P/L, wallet-vs-ledger reconciliation, risk flags), `auditGuild` (money supply, loans, open interest incl. 0DTE expiring today, concentration/HHI, engine activity), `leaderboard` (ranked by **equity**, so a wallet full of borrowed points is not a big account), and `reconcile` (nine invariants; a new instrument should add its invariant here rather than trusting it).
- Commands: `/options` (incl. `write`, `buyback`, `spread`), `/margin`, `/orders`, `/predict`, `/futures`, `/wheel`, `/exchange`, plus `short`/`cover` on `/stocks`. Tools: `optionChain`, `tradeOption` (incl. write/buyback), `shortStock`, `marginAccount`, `exchangeOrder`, `eventContracts`, `tradeSpread`, `tradePerp`, `goblinWheel`, `auditAccount`, `auditExchange` — all in `VOICE_TOOL_NAMES`. `auditAccount` resolves **any guild member** by mention, id, username, or display name via `resolveGuildMember` (`"you"` = Goobster's own account). Tool actions that change how much risk an account can take (margin, leverage, Goblin Mode) or spend other people's wallets (the Wheel) refuse to run without `confirm: true`, so the model must explain the risk and get an explicit yes first.
- Event contracts settle **deterministically from the feed** (`predictionService`): a market names a real symbol, threshold, and resolution time, and the price is read at that time — no oracle, and no admin decides who won. Prices are the risk-neutral probability (`N(d2)`, the same machinery as the option chain) plus a fixed house edge; per-trader position caps stop one whale owning an outcome; `voidMarket` refunds at cost.
- Privacy: every exchange table is per-user financial data and is **deleted outright** by `/forget-me` (`exchange_accounts`, `short_positions`, `option_positions`, `option_trades`, `exchange_orders`, `prediction_positions`, `exchange_events`, `perp_positions`, `exchange_optins`); a market the user created survives with `createdBy` nulled. All nine are counted by `auditUser` and reported by `/what-do-you-know-about-me`. Any new exchange table must be added to all three paths.
- **Tool account identity is explicit** (`resolveEconomyAccount` in `utils/toolsRegistry.js`): `checkPoints`, `tradeStock`, and `checkPortfolio` take an `owner` parameter — `"user"` (default) acts on the requesting human's wallet, `"bot"` acts on Goobster's **own Discord account** (`interactionContext.client.user.id`, the same real id `/points admin grant` can fund — never a synthetic id), so "check/spend *your* points" reaches the shared `economyService` wallet keyed on `(guildId, botUserId)`. `gamblePoints` is deliberately user-only (the games are player-vs-bot). Tool results name the wallet they acted on so the model can't misattribute balances.
- Privacy: economy data is **deleted outright** on `/forget-me` (wallet, ledger, holdings, trades — personal financial data, not aggregate accounting), reported by `/what-do-you-know-about-me`, and covered by `auditUser`.

### Multiplayer table games (Discord Activity)
- **Architecture rule: engines are pure, the manager owns side effects.** Game engines under `services/tableGames/` (`blackjack.js`, `roulette.js`, `baccarat.js`, `holdem.js`) are pure state machines: `createTable()`, `applyAction(state, action, rng) -> { state, events, charges }`, `getView(state, userId)` (per-player view; hidden information like the dealer's hole card and the deck never leaves the server), `getEscrowRefunds(state)`, `isEmpty(state)`. No database, no timers, no Discord, injectable RNG — fully deterministic under test. New games implement this interface (shared `GameError` lives in `gameError.js`) and register in `ENGINES`; their player actions must also be added to the WebSocket action allowlist in `web/activityApi.js` and get a renderer module under `web/activity/games/`.
- `services/tableGames/tableManager.js` is the only side-effect zone: one live table per guild+channel, and every transition **commits engine `charges` through `economyService.adjust()` and journals the new state (`table_games` row) in a single SQLite transaction** — a bet can never be escrowed without the state that took it being durable, and an unaffordable bet rolls the whole transition back (`INSUFFICIENT_FUNDS` surfaces to the client, state unchanged). Engines declare timers in `state.timer`; the manager schedules the system action (`timeout-act` auto-stand, betting-window `deal`/`spin`, `next-hand`/`next-round`) and tolerates stale fires. On boot, `recoverFromJournal()` refunds bets escrowed in crash-interrupted hands (ledger type `table-<game>-refund`) and clears the journal; the journal is transient (deleted when tables close), so it adds no `/forget-me` surface.
- **Game selection**: the client lobby sends `gameType` with the WebSocket `join`; `getTable` keeps the one-table-per-channel invariant by switching an existing table's engine **in place only when it has no seated players** (subscribers stay attached and receive the fresh state) — with players seated, the running game wins and later joiners land in it. A `leave-table` message returns a socket to the lobby (vacating the seat, with the engine refunding any betting-phase escrow).
- House rules (v1): **Blackjack** — 4-deck shoe per hand, dealer stands on all 17s, blackjack pays 3:2 rounded down, double on any first two cards, no splits, 5 seats. **Roulette** — European single zero, simultaneous betting (no turn order), straight 35:1 / dozens+columns 2:1 / even-money 1:1, zero kills outside bets, up to 20 stacked bets per seat with `clear-bets` refund, 8 seats. **Baccarat** — punto banco tableau (no post-bet decisions; deal and settlement are one transition), 6-deck shoe per round, banker win pays 1:1 minus 5% commission rounded down, tie 8:1, player/banker push on tie, 7 seats. **Texas Hold'em** — no-limit with rotating button and `minBet/2`/`minBet` blinds (heads-up: button posts small), wallet-backed betting (chips escrow into the pot as they're bet; no stacks/all-ins/side pots, street raise-to capped at `maxBet`, can't-cover-the-call means fold), single deck per hand, ties split with the odd chip to the earliest seat, 6 seats. Hold'em is the first game with hidden information: `getView` reveals hole cards only to their owner (showdown reveals via `results`), and mid-hand leavers fold, forfeiting chips already in the pot while `contributions` tracks per-user escrow for crash refunds. **Slots** — a bank of classic 3-reel machines (one per seat, 6 seats) pulled together: shared betting window, all reels spin and settle in one transition; a weighted 21-stop strip and a first-match paytable (triple 7s pay 150x total, down to money-back cherry pairs) give the house roughly a 7% edge. **Casino War** — 6-deck shoe per round, one card per bettor vs. one communal dealer card, higher rank wins even money (aces high), 6 seats; a tie moves that seat to the simultaneous `war` phase (timer auto-surrenders): surrender returns half the bet rounded down, war escrows a matching bet and deals fresh cards (communal dealer war card), where winning returns both bets plus even money on the original and tying doubles that bonus. **Craps** — street rules, 8 seats, no turn order: pass/don't pass are come-out-only line bets (naturals/craps per the book, don't pass pushes on 12), the field is a single-roll bet open before every roll (2 and 12 pay 2:1, other field numbers 1:1); a round runs come-out → point → made/seven-out with the table auto-rolling on a timer (any bettor can throw early), field bets resolving mid-round via each seat's `resolved` list, and per-seat net outcome computed at settlement. Leaving with the point on refunds field bets but line bets must ride (seat flagged `left`, cleared after settlement). **Let It Ride** — single deck, 6 seats, hidden information: the ante escrows three equal bets, three cards per player + two face-down community cards; before each reveal every in-hand player simultaneously rides or pulls one bet back (timeout pulls — the safe default; pulls refund immediately), the third bet always rides, and the final 5-card hand pays all riding bets per the standard paytable (tens-or-better 1:1 up to royal 1000:1). `getView` hides hole cards from other players until showdown and reveals community cards by phase; mid-hand leavers auto-ride to showdown.
- **Goobster plays too** (`services/tableGames/botPlayer.js`): a side-effect service — never engine code — that subscribes to a table like any client, watches its own personalized view, and acts through `tableManager.act` (seated with an `isBot` flag only trusted server code can set; the WS layer never forwards it — every engine stores/exposes it per seat). **Every game is decided by the model, never by built-in strategy**: the per-game `ADVISORS` registry exposes `needsAction(view)`, `buildDecisionContext(view, { persona, balance, currencyName, images })` (serializes the full game state plus the same options a human player has into an ONLY-JSON prompt; `images` is the extension point for feeding table screenshots to vision models), `legalize(decision, view)` (the validator — repairs/clamps model output into `{ actions: [...] }` legal engine moves, `{ pass: true }` to sit a round out, or `null` for unusable responses), and `fallback(view, rng)` (plays ONLY when no provider produces a usable answer). The configurable `activity.bot.persona` is injected into every decision prompt so it shapes risk appetite and bet sizing, not just table talk. In the chance games the bot follows, never leads (it only bets into a round a human opened, and never force-deals/spins). A rejected action takes the advisor's `retreat` (check/fold/stand) or sits the round out (`skipKey` prevents retry loops); multi-move decisions (e.g. a roulette bet spread) stop cleanly at the first failed follow-up. The bot banks through the normal economy (`bot-bankroll` top-ups when low, refreshed on every settle), is invited/dismissed via WS `invite-bot`/`dismiss-bot` (inviter must be seated), and auto-leaves when the last human stands. Table talk goes to Activity clients via `tableManager.notify` (`chat` messages), optionally to the channel (`activity.bot.textComments`), and — with `activity.bot.voiceComments`, default on — out loud whenever the bot is already in a guild voice channel: a live `/voicechat` session's TTS pipeline is preferred, otherwise any existing voice connection (`getVoiceConnection`) plus `serviceManager.voiceService.tts`; it never joins voice itself. In hidden-information games, mid-hand comments run through the advisor's `sanitizeComment` (`leaksHiddenCards`): any card glyph, card-rank word, hand-strength term, or the bot's hole ranks as digits gets the comment dropped — prompts forbid reveals, the filter guarantees it. All bot AI calls carry `usageContext` and comments are rate-limited per table.
- The Activity backend (`web/activityApi.js`) is **opt-in** (`config.activity.enabled`) and mounts on the public health server, since Discord's proxy must reach it (see `documentation/activity_setup.md`; a cloudflared tunnel is the recommended exposure). Auth: the embedded client exchanges its SDK `authorize()` code at `POST /api/activity/token` (client secret from `DISCORD_CLIENT_SECRET` or `config.activity.clientSecret`), the server resolves identity via `/users/@me`, and WebSocket joins verify **actual guild membership through the bot client** before letting anyone spend that guild's points. `config.activity.devMode` mints browser-testable identities and skips those checks — never enable it on an exposed server. Sessions are transient/in-memory (re-derivable by re-auth, allowed exception to the SQLite rule).
- The client (`web/activity/`, plain browser ES modules like the panel) auto-detects Discord via the `frame_id` query param: inside Discord all requests use the `/.proxy/` path and context comes from the SDK; otherwise a dev-mode identity form appears. `@discord/embedded-app-sdk` is served directly from `node_modules` (its ESM output uses only relative imports — no bundler). Sound effects are synthesized with WebAudio (`sounds.js`) — no audio assets, muting persists in localStorage, and the AudioContext is created lazily on first gesture (autoplay policy).
- Client visuals: static art lives in `web/activity/assets/` (AI-generated, downscaled webp: per-game lobby covers and the Goobster dealer avatar shown at each table, which does a CSS "dealing" flourish on card events). Wagers and the hold'em pot render as chip piles (`chips.js`: greedy denomination stacks, pure CSS), and every broadcast's events drive flying-chip animations (bets fly to the seat, payouts fly from the dealer/bank to winners, lost bets are raked in) in a fixed overlay that survives re-renders. **Bet input rule**: every broadcast fully re-renders the action bar, so the shared amount control (`ui.js` `betAmountControls`) keeps unsubmitted edits and focus in a module-level draft keyed by storage key, restored into the rebuilt input — renderers must clear the bar via `resetActionBar()` (never `replaceChildren()` directly) so focus tracking works. The control has red subtract chips on the left and green add chips on the right (clamped at the table minimum).
- Background music: `GET /api/activity/music/casino` generates a 2-minute instrumental lounge track **once** via the ElevenLabs Music API (`elevenLabsAudioService.generateMusic`, same optional paid plan as `/playmusic`), caches it at `cache/music/casino.mp3`, and serves it from disk thereafter; without a key it returns 404 and the client stays silent (graceful degradation). The client loops it through a dedicated WebAudio gain node with a fade-in, gated on the first user gesture, with an independent 🎵 mute persisted in localStorage. Music and effects are per-viewer — never injected into the voice channel.

### The web app (browser chat + memory dashboard)
- A browser interface served by the bot itself (`web/appApi.js` + the static client in `web/app/`, plain ES modules like the panel and Activity). **Opt-in** via `config.webapp.enabled`; mounts on the public health server (`/app`, `/api/app/*`) because it must be reachable through the same tunnel as the Activity. Setup: `documentation/webapp_setup.md`.
- **Auth**: standard OAuth2 authorization-code redirect (`identify` scope only; the access token resolves the user once and is never stored). Sessions are **SQLite-backed hashed tokens** (`web_sessions`, `services/webSessionService.js`, 30-day TTL) in an httpOnly SameSite=Lax cookie - unlike the Activity's transient in-memory sessions, a Pi reboot must not log web users out. `webapp.devMode` mints browser-testable identities and must never be enabled on an exposed server. `/forget-me` deletes the user's sessions (`counts.webSessions`) and `auditUser` counts the table.
- **Web chat reuses the whole chat pipeline, not a parallel one**: `services/webChatService.js` builds a web-shaped pseudo-interaction (the `createPseudoInteraction` pattern) and calls `handleChatInteraction`. The pipeline understands four web capabilities: `onStreamDelta` (raw token deltas over SSE instead of throttled Discord edits), `sendFullResponse` (whole replies via `responder.deliverResponse` - Discord's 1900-char chunking is a platform limit, not a product decision), `maxInputLength` (20k chars for long pastes), and `shouldAbort` (the Stop button - forwarded to `runAgentLoop`, which halts at the next round boundary; an abort with partial text delivers and stores the partial ChatGPT-style, an abort before any text stores just the user message and ends quietly). Never fork the pipeline for the web - extend the capability set instead.
- **Conversation model** (the ChatGPT-style sidebar): each conversation is a `web_conversations` row (userId, unique `channelId` of the form `web:<userId>:<key>`, title, activity timestamp) whose messages live in the normal chat tables. All conversations share the user's DM scope (`dm:<userId>`), so long-term memory, facts, nicknames, and personality settings are shared with Discord DMs while each conversation keeps its own context window - rebuilt from the `messages` table (the pseudo-channel's `messages.fetch` reads SQLite, newest-first with a `.size` property), so history survives restarts. "Edit & resend" and "Regenerate" share one primitive (`truncateFrom`: delete a message row and everything after it, then send a fresh turn). Titles are auto-generated (immediate fallback from the first message, fire-and-forget model-written replacement). Pre-sidebar web chats (`web:<userId>` channels) are adopted lazily as "Earlier conversation" - never dropped. `web_conversations` is deleted by `/forget-me` and counted by `auditUser`.
- **AI settings from the web portal**: the header model chip opens a settings modal with provider (from `aiService.listProviders()` - the configured catalog with default models and reasoning-effort support, never hardcoded model ids in the client), model override, and reasoning effort, persisted via `webChatService.setAiSettings` to the user's DM scope through the same `setGuildAI` storage `/aisettings` uses - the web UI and the Discord command stay in lockstep by construction. Thoughtful Mode remains the one-click preset on the same storage (`aiService.getThoughtfulPreset`).
- **Incognito mode**: a header toggle makes turns transient. `webChatService.startTurn({ incognito: true })` sets `skipHistory` on the pseudo-interaction; `chatHandler` then skips every SQLite write (users/conversations/messages rows, memory writes, summaries - `chatContext.summarizeContext` also guards on a null `guildConvId`), filters out the `rememberFact` tool, and tells the model it is an incognito conversation. Context comes from a bounded in-memory window per user (24 messages, 2h TTL - an allowed exception to the SQLite rule precisely because persistence is the thing being opted out of); leaving incognito or restarting evaporates it. The web client keeps its own local-only transcript for export.
- **Text/document attachments**: beyond vision images, the composer accepts text-shaped files (md/csv/json/code/...). They are validated server-side (4 files, 50k chars each, 120k combined, control characters stripped from names) and folded into the pipeline message with a parseable `[Attached file: name]` + fenced-block marker format - the same composed text is what history stores, and the client splits the markers back out into collapsible attachment chips when rendering. No separate attachment storage, no divergent history shape.
- **PDF attachments**: PDFs upload as base64 and are converted to text server-side (`webChatService.extractDocumentFiles`, `pdf-parse`, 8MB cap, truncated to the text-file cap with a visible note) *before* `startTurn` runs, so extraction failures stay proper HTTP errors instead of mid-stream SSE errors; the extracted text then rides the normal text-attachment path. Scanned PDFs with no extractable text are rejected with a clear message rather than sent as empty context.
- **Tool-activity streaming**: `agentOrchestrator.executeToolRound` emits `onToolEvent({ phase: 'start'|'result', name, cached, isError })` per tool call; `chatHandler` forwards the hook only when the interaction provides it (a web capability, like `shouldAbort`), `webChatService` maps it to the turn's `events.onTool`, and `appApi` streams SSE `tool` events. The client shows chips ("Searching the web…" → ✓/⚠) in an activity strip that is removed when the reply lands - the stored tool transcript remains the durable record. Hooks are cosmetic and must never break the loop (all wrapped in try/catch).
- **Uploaded image persistence**: user vision uploads are saved to `data/web-uploads/<userId>/` with content-hash filenames (`utils/webUploads.js`) and written onto the user message row as `metadata.attachments` - the same shape the bot's generated files use, so `getHistory` re-serves them through the owner-bound file route and images survive reloads. Incognito turns never write uploads. `/forget-me` deletes the whole per-user directory (`counts.uploadedFiles`) and `auditUser` counts leftover files (`web_upload_files`).
- **Full-text message search**: `webChatService.searchMessages` runs a LIKE scan (wildcards escaped, ≥2 chars, bounded results with snippets centered on the first hit) joined through `web_conversations` so it is strictly user-scoped; served at `GET /api/app/chat/search`. The sidebar box filters titles instantly and debounces the server search, and clicking a hit opens the conversation and scrolls to/highlights the message (`data-msg-id`). LIKE over SQLite is the deliberate choice at self-hosted scale - no FTS index to maintain.
- **Per-user custom instructions**: the ChatGPT-style "how should Goobster respond" text, stored on `UserPreferences.custom_instructions` (`utils/userInstructions.js`, 2000-char cap). `chatHandler` appends the block on **every** surface (web, DMs, guilds) *before* the personality directive, whose explicit override clause keeps guild directives authoritative on conflict. Edited from the web settings modal (`customInstructions` on the settings routes) or `/instructions` in Discord (view/set/clear, ephemeral). Included in the transparency report; erased with the UserPreferences row by `/forget-me`.
- **Guardrails**: one in-flight turn per user (`stopTurn` aborts it) with a **15-minute watchdog** (`_liveTurn`: a turn older than `TURN_MAX_AGE_MS` is force-aborted and its lock released, so a stalled provider stream can never lock the user out of the portal until the next restart) and a real `AbortController` per turn whose signal rides `interaction.abortSignal` → `chatOptions.signal` → the provider request/stream (OpenAI SDK per-request `signal`; Anthropic/Gemini `fetch` `signal`) — Stop and the watchdog hard-cancel in-flight network calls instead of waiting for the next round boundary, and `chatHandler` ends deliberately-aborted turns quietly instead of apologizing; a 10-turns/minute sliding-window rate limit (validation errors throw *before* the SSE stream starts so they remain proper HTTP statuses), an Origin guard on state-changing requests, vision attachments validated server-side (max 4 image data URLs, ~6MB each - the JSON body limit on `/api/app` is sized for this), and image-tool output served through an owner-bound authenticated file route (in-memory registry - transient, re-derivable). Errors use `WebChatError`/`WebDashboardError` (status + machine-readable code, the `PanelError` contract).
- **Memory dashboard access model** (`services/webDashboardService.js`): a user's DM scope is wholly their own (browse/delete everything in it); in a guild scope they must be an actual member (verified through the bot client, like the Activity WS join) and only see/delete memories and facts **about themselves**; the knowledge-graph view (nodes/edges + recent monologue thoughts + scratch pad) requires **Manage Server**, mirroring `/monologue graph`. Every memory deletion calls `memoryService.cleanupVecIndex()`.
- The client renders Markdown with a small escape-first renderer (`web/app/markdown.js` - no dependency, everything HTML-escaped before markup is generated), highlights code with a tiny tokenizer (`web/app/highlight.js` - comments/strings/numbers/keywords, output exactly as safe as escaping), and draws the knowledge graph with a dependency-free canvas force layout (`web/app/graph.js`). Chat UX features (conversation sidebar with rename/delete/search, stop, regenerate, edit & resend, image attach/paste with client-side downscaling, copy buttons, Markdown export, light/dark theme) live in `web/app/chat.js` - still plain ES modules, no framework.
- **LaTeX math renders with KaTeX** - the one deliberate exception to the dependency-free client, served straight from `node_modules` at `/app/vendor/katex` (the embedded-app-sdk precedent - no CDN, self-hosted first). `markdown.js` extracts math segments (`$$..$$`/`\[..\]` display, `\(..\)` inline, and a conservative single-`$` form that refuses whitespace-adjacent matches so "$5 and $10" stays prose) into placeholder spans carrying the escaped TeX; `web/app/math.js` lazy-loads KaTeX on the first message that actually contains math and typesets in place (`throwOnError: false`, `trust: false`). Without KaTeX (load failure, old cache) the escaped TeX source stays visible - graceful degradation, never broken markup. Extraction order matters: fenced code beats math, math beats inline markdown (TeX underscores/asterisks must survive).
- **Mini-apps (the web-chat canvas)**: an assistant ` ```html ` (or ` ```svg `) fenced block renders as a live interactive app instead of a plain code block - `web/app/codeblocks.js` (shared by the chat AND the parlor) builds an "applet" card with Preview/Code tabs, restart, fullscreen, and download-as-file, and also renders tool-file attachments (images inline, other files as download chips). The iframe sandbox is `allow-scripts allow-modals allow-popups` and deliberately **never** `allow-same-origin`: generated code runs on an opaque origin with no path to the session cookie, the API, or the parent DOM. There is intentionally no "open in new tab" via blob URL (a blob document would inherit the app origin and could reach the API with credentials); download-to-file is the escape hatch. The model learns about the canvas from a prompt block in each surface's own prompt builder: `chatHandler` appends `WEB PORTAL RENDERING` for `web:` channels (Discord chats never get it), and `parlorService._buildPersonaMessages` carries a matching `RENDERING` section so personas build mini-apps too (parlor generation bypasses `chatHandler`).
- **Mobile**: below 720px the sidebar is a fixed slide-in drawer (`#sidebar.open`, backdrop click and any in-drawer navigation close it; row-level edit controls don't), the layout uses `100dvh` + `env(safe-area-inset-bottom)`, the composer input holds 16px font so iOS doesn't zoom on focus, and hover-revealed actions (message actions, conversation rename/delete) are always visible under `@media (hover: none)`. The chat header keeps only the ☰ drawer button, the title, the model chip, and a **⋯ menu** on a phone: `#chat-more-menu` is `display: contents` on desktop (the actions sit inline exactly as before) and becomes an anchored dropdown under 720px, so Thoughtful/incognito/share/integrations/export never compete for the row. Header layout rules are **overlap-proof by construction**: `.chat-header-actions` shrinks (`flex: 0 1 auto`) and the model chip's label ellipsizes, while `.title-row` deliberately has no `min-width: 0` so its automatic minimum size is the hamburger's width - a crowded header can shorten the title, never slide a control on top of ☰.
- **Voice in the browser** (`services/webVoiceService.js`, routes under `/api/app/voice/*`): the composer 🎤 dictates (browser MediaRecorder clip → base64 → batch STT: OpenAI transcription via the existing `transcriptionService` — generalized to accept webm/ogg/mp4 clips — falling back to ElevenLabs Scribe batch when only that key exists), and every reply gets a 🔊 Listen action (server-side markdown-to-speech cleanup — code/math/URLs never reach the audio, the voice-stack rule — then the **shared** `/setvoice`-configured ElevenLabs TTS service's MP3 stream piped to the browser, with a direct-fetch fallback). `GET /voice/capabilities` gates the buttons: no keys means they never render — graceful degradation, never an error. Nothing persists (no new privacy surface); per-user rate limits are transient in-memory state.
- **Message branching** (`webChatService.branchFrom`): editing an earlier message offers **⑂ Branch** beside Save & resend — history *before* the branch point is copied (authorship, timestamps, metadata) into a fresh conversation whose row records `parentConversationId`/`branchedFromMessageId`, and the edited text is sent there as a normal turn. The original conversation is untouched (the whole point), and the chat pipeline never learns about branching: the copied rows ARE the context. Deleting a parent detaches (never deletes) its branches. Truncate-and-resend remains for destructive edits.
- **Read-only share links** (`web_share_links`, one per conversation): 🔗 creates a revocable public link (`/app/share/<token>`) served by a standalone viewer that reuses the markdown/math/code renderer modules. `GET /api/app/share/:token` is deliberately unauthenticated — the unguessable token is the capability, the query starts at the token so no other conversation is reachable, and the payload carries text only (no owner ids, no attachment URLs — files stay behind the owner-bound route). The token is stored in plaintext, a deliberate exception to the hashed-session rule: it only reveals content living in the same database rows, and hashing would break "copy the link again later". Revoking (or deleting the conversation, or `/forget-me`) kills the URL instantly.
- **Scheduled tasks in the portal** (`services/webTaskService.js`, the Tasks pane): surfaces the existing `automations` (recurring cron, 15-minute floor enforced by sampling the next fires) and `followups` (one-shot reminders, plus chat-scheduled recurring follow-ups shown with their recurrence label and delivery count; cancelling one ends the series) — view/create/toggle/cancel. Portal-created tasks live in the user's DM scope (`dm:<userId>`) and deliver to their Discord DM channel; `automationService.executeDmAutomation` runs them through `handleChatInteraction` with a DM-shaped pseudo-interaction (guild null → the pipeline resolves the DM scope; `sendFullResponse` delivers banner-first and chunked) — never a parallel executor. Discord parity: `/automation` is DM-enabled on the same rows. Guild automations the user owns are listed and cancellable (the authority `/automation delete` already gives them); creating guild automations stays Discord-side.
- **Personal usage dashboard** (`webDashboardService.getUsageStats`, the Usage pane): the user's own `usage_log` rows — totals, per-model, per-operation, per-day — over a clamped window, drawn with a dependency-free canvas bar chart. Token counts only: `usage_log` records no prices, so the portal never invents dollar figures.
- **Memory retention from the portal**: the Memory overview (DM scope only) sets `guild_settings.memory_retention_days` on the user's own `dm:<userId>` scope with an immediate purge + `cleanupVecIndex()`, exactly like `/privacy retention`. Guild retention stays a Manage Server action in Discord. Parity: `/privacy` is DM-enabled (`status`/`retention` work in DMs under the DM-admin rule; channel exclusions stay guild-only).
- **PWA**: `manifest.webmanifest` + icon set + `sw.js` make the portal installable. The service worker is network-first for `/app/` static files only (fresh code always wins when online; the cache answers offline) and **never** intercepts `/api/*` (auth, SSE, live data). Share URLs (`/app/share/*`) stay live-only. Bump `CACHE_NAME` whenever the precached shell list changes, so `activate` drops the stale cache.
- **The mark**: `web/app/icons/goobster.svg` is the logo - a flat, gradient blueberry with its calyx crown, hand-authored vector, no dependency. It is the source of truth: the favicon, the in-app brand/login/empty-state logos, and the rendered `icon-192.png`/`icon-512.png` all point at it, and those PNGs are **transparent** so an OS shortcut rounds the berry instead of a dark square. Two variants exist because their consumers demand opacity: `goobster-maskable.svg` (→ `icon-maskable-512.png`, full-bleed brand plate with the mark inside the 80% safe circle, per the maskable spec) and `apple-touch-icon-180.png` (iOS composites transparency onto black). Re-render after editing a source SVG: `google-chrome --headless=new --default-background-color=00000000 --screenshot=icon-512.png --window-size=512,512 file://$PWD/web/app/icons/goobster.svg` (the smaller sizes are downscales of that render).
- **Accessibility**: `web/app/modal.js` is the one dialog helper (focus trap, Escape, backdrop click, focus restore) and every modal uses it — including the parlor's and the confirm dialog. Icon-only buttons carry `aria-label`s, the toast is a polite live region, sidebar conversation rows are keyboard-activatable, `:focus-visible` outlines are global, and `prefers-reduced-motion` disables animations (including JS smooth-scrolling).
- Privacy: the new surfaces are covered — `automations` (owned rows deleted by `/forget-me`, listed per-scope in the transparency report, counted by `auditUser`; this also closed a pre-existing gap), `web_share_links` (deleted, counted, reported), and the DM scope's `guild_settings` row (AI overrides, directive, retention — deleted and audited).

### Personal platform integrations (Notion, GitHub)
- The ChatGPT-style "connectors": a user connects their own Notion workspace or GitHub account through the web portal's Integrations dialog, and the chat agent's tools can then reach that user's data in their DMs and web chats. Catalog + storage in `services/userIntegrationService.js`, table `user_integrations` (userId + provider PK, raw token, `accountLabel` display snapshot, timestamps).
- **The raw token is stored deliberately** - it is replayed against the provider's API on every tool call, the same trust model as `config.json`'s global `GITHUB_TOKEN` but scoped to one user. Connecting verifies the token live (`githubService.withToken(token).getViewer()` / `notionService.getViewer(token)`) and snapshots a "Connected as ..." label; a token the provider rejects is never stored. Tokens are never sent back to any client, and the transparency report names providers + labels only.
- **Access rules live in the tools** (`utils/toolsRegistry.js`): `searchNotion`/`readNotionPage` exist only in DM/web scope with a connected Notion account (`resolveNotionAccess`); the GitHub tools use the guild allowlist in servers as before, and fall back to the user's personal token in DMs/web (`resolveGithubAccess`). A user's token never acts in a guild context.
- `services/notionService.js` is **read-only by design** (workspace search + page text; blocks flattened to markdown-ish plain text, bounded depth/length) - grounding answers in the user's notes, not writing to them. `githubService.withToken()` returns a per-token instance so user-scoped calls share all the existing request/error plumbing.
- **Connecting is web-only**: the Discord `/integrations` command (DM-enabled, always ephemeral) shows status and disconnects, but deliberately has no connect path - pasting API tokens into a Discord message is a habit the bot must not encourage.
- Privacy: `/forget-me` deletes `user_integrations` outright (credentials are the most urgent thing to erase), `auditUser` counts the table, and `buildUserReport` lists connected providers (never tokens).

### The Parlor (multi-persona AI workspace in the web app)
- A third web-app pane (`web/app/parlor.js` + `parlorWorkspace.js` + `parlorUi.js`, routes in `web/appApi.js` under `/api/app/parlor/*`, service in `services/parlorService.js`) where a user converses with a small cast of **personas** they create, and conversations become persistent, evolving knowledge instead of disappearing when the chat ends.
- **Tag-first knowledge model** (the Spitball design): each persona has a private workspace of notes (`parlor_notes`) that never link to each other directly - **tags** (`parlor_tags`, `parlor_note_tags`) create the relationships, so notes sharing a concept connect automatically and the graph stays emergent instead of hand-maintained. Users seed and edit notes directly; the AI can suggest tags (existing tags preferred - concept reuse is the point). Per-note embeddings power semantic search (bounded brute-force cosine over one persona's notes, ≤500 - deliberately **not** the sqlite-vec index; keyword fallback when no embedding backend or the vector hasn't landed). Note embeddings are computed fire-and-forget on write, same rule as memory writes.
- **The fixed respond workflow**: every persona reply runs retrieve (semantic search over its own workspace) → generate (grounded in the retrieved notes, which are stored on the message as `contextNoteIds` - **traceable context**, rendered as grounding chips) → write back (an ONLY-JSON extraction pass proposes at most 2 durable notes from the exchange; deterministic code legalizes - length caps, per-persona caps of 500 notes/150 tags, title dedupe via `UNIQUE (personaId, title)`, tag normalization - and stores them with `source = 'conversation'`). The model proposes, the service decides - the same trust boundary as the monologue graph and the campaign forge. A failed write-back costs learning, never the reply.
- **Personas are tool-using conversation partners**: the generate step runs through the shared `runAgentLoop` (never a parallel tool loop; voice-sized `PERSONA_MAX_TOOL_ROUNDS` = 3) with the curated `PERSONA_TOOL_NAMES` subset - `performSearch`, `generateImage`, `runCode` (auto-filtered when the sandbox is off; the parlor's synthetic `web:parlor:...` channel id satisfies the sandbox's web scope), `rollDice`, `stockQuote` - plus native web search when the provider supports it. Deliberately excluded: `manageParlor` (a persona rewiring the parlor mid-turn would break it), Goobster's own memory tools (personas have their own workspaces), and everything guild-/channel-/identity-bound. The system prompt orders in-character tool use ("use them the way your charter would") without naming tools. Tool file output (generated images, sandbox charts) is captured by the persona tool context instead of a Discord send, persisted on `parlor_messages.attachments` (paths; column added via `applyColumnMigrations`), and re-served through the owner-bound `/api/app/files` route (`webChatService.registerFile`). Tool rounds stream a `persona_tool` SSE event so the client resets its draft and shows what the persona is doing.
- **Multi-persona discussions** (`parlor_conversations` / `parlor_participants` / `parlor_messages`, up to 4 seats): every participant replies in seat order over one SSE stream (`persona_start`/`persona_pass`/`delta`/`persona_tool`/`persona_message`/`learned` events); each persona sees other personas' replies as labeled user messages and is told to engage and disagree freely - distinct perspectives are the point, and because each keeps its own workspace they develop different expertise over the same conversation. One persona's generation failure emits an error message event and the turn moves on. Persona names are snapshotted on messages (`personaName`) so transcripts survive persona deletion.
- **The should-respond gate**: in a group discussion each persona first *considers* whether it has something to say (a cheap ONLY-JSON call over the charter + a short history tail + who already replied). Legalization is deliberately permissive - only an explicit `"respond": false` silences; a broken gate never mutes a persona. Deterministic pre-pass: a direct name-mention always speaks (word-boundary match, first name included). Solo discussions and manual triggers skip the gate, and when every participant declines the first seat is re-run forced - the user never gets silence. Declines emit `persona_pass` (rendered as a "listens quietly" line, reason in the tooltip) and are never stored.
- **Manual persona trigger** (`startPersonaTurn`, `POST /api/app/parlor/conversations/:id/personas/:personaId/respond`): make one seated persona respond right now - no new user message, no gate, even if they just spoke (storytelling rounds, long-form planning). In the UI, clicking a participant chip nudges that persona. Same turn lock and rate limit as normal turns; requires the persona to be seated (`NOT_SEATED`).
- **Ownership and guardrails**: everything is keyed on the web user's snowflake (`ownerId`) and every access check lives in the service (routes stay thin). `ParlorError` follows the `PanelError` status+code contract. One in-flight turn per user, a 6-turns/minute sliding window, 8k-char message cap, 12 personas per user. AI usage is attributed to the user's DM scope (`usageContext`). Deleting a persona cascades its whole workspace; deleting a discussion keeps the personas and everything they learned (knowledge outliving the conversation is the feature).
- **Quickstart** (`parlorService.quickstart`, `POST /api/app/parlor/quickstart`): one topic brief bootstraps a whole salon - an AI concierge designs 2-4 personas with distinct perspectives, charters, and 1-3 seed notes each (ONLY-JSON), and deterministic code creates everything **through the normal CRUD paths** so every cap, dedupe, and normalization rule applies automatically; unusable proposals are skipped, never repaired. A discussion is opened with the new cast, titled from the design, and the suggested opening message is returned for the composer. The empty-parlor UI offers quickstart as the featured first-run path (starter cast and manual creation remain). No provider → `QUICKSTART_UNAVAILABLE` (503), manual paths still work.
- **Goobster operates the parlor by tool-use**: the `manageParlor` tool (`utils/toolsRegistry.js`, available to text chat everywhere - it is not in the voice subset) lets the chat agent inspect and build the requesting user's parlor on their behalf: `overview`, `quickstart`, `create-persona`/`update-persona`, `list-notes` (browse or semantic search), `create-note`/`update-note`, `create-conversation`/`rename-conversation`, `add-participant`/`remove-participant`. It is keyed to `interactionContext.user.id` only (never another user's parlor), surfaces `ParlorError` as friendly text, and **deliberately has no delete actions** - destructive operations stay in the web UI where the user confirms them.
- **Multi-user parlors (shared discussions)**: the owner can invite Discord friends into one of their discussions. `parlor_invites` (pending/accepted/declined/revoked, owner-only to create, cap of 4 humans per discussion counting pending invites) hangs off the conversation root; accepting creates a `parlor_members` row (userName snapshotted). Invites are delivered as a **DM with accept/decline buttons** (`accept_parlorinvite_<id>` / `decline_parlorinvite_<id>`, routed by `events/interactionCreate.js` to `parlorService.handleInviteButton` - state in SQLite, restart-safe like the tavern buttons) *and* appear in the invitee's web app (`GET /api/app/parlor/invites` + respond route), so closed DMs never block joining. A failed DM is reported (`dmSent: false`), never an error. The chat agent can invite on the user's behalf (`manageParlor` action `invite-user`).
- **Member access model**: `_requireConversationAccess` (owner OR member; strangers get the same 404 as a missing discussion) gates the shared surface - transcript reads, `startTurn`, `startPersonaTurn`, and the member roster. Everything management-shaped stays owner-only through `_requireConversation`: persona seats, rename/delete, inviting, revoking. The owner removes anyone; a member removes only themself (leave). Personas, their workspaces, and **AI usage attribution stay the owner's** (the host pays for their own salon); rate limits apply to the requesting user, and the in-flight turn lock is **per conversation** (keyed by conversation id, remembering `startedBy` so `stopTurn` only stops your own turn). `parlor_messages` user rows snapshot the speaker (`userId`/`userName`, columns added via `applyColumnMigrations`); persona prompts label each human by name so the cast can tell members apart, and transcript attachments are re-registered to the *viewer* so the owner-bound file route serves members too. The client polls lightly (5s, visible pane only) so other members' turns land without a refresh.
- **Parlor Live (real-time voice sessions)**: a discussion can "go live" (`services/parlorLiveService.js`, `WS /api/app/parlor/live` attached by `attachWebAppWebSocket` in `web/appApi.js` — the gbaRunApi noServer-upgrade pattern, but authenticated BEFORE the upgrade completes with the same session cookie + Origin guard the REST API uses; membership via `parlorService.requireConversationAccess` on join). Humans stream mic audio up as 16kHz mono PCM (an AudioWorklet resamples in the browser — `web/app/liveAudioWorklet.js`); the server buffers behind an RMS energy gate (open-mic noise never reaches paid STT), streams hot audio into **Scribe v2 Realtime** while the user talks, and commits on the client's silence gate (~900ms), with per-utterance batch STT fallback through `webVoiceService.transcribe` when the realtime API errors. **Committed utterances become normal parlor turns through `startTurn`** — never a parallel generation path — so the gate, retrieval, tools, write-back, rate limits, and the per-conversation turn lock all apply; utterances that land mid-turn queue (bounded) and the lock arbitrates. Turns started outside the session (a member typing through the SSE route) are tapped in (`observeTurn`) so typed turns render live and are voiced too — one pipeline, two transports.
- **Per-persona voices**: `parlor_personas.voiceId`/`voiceName` (columns added via `applyColumnMigrations`), resolved through `elevenLabsTTSService.resolveVoice` **at save time** (`parlorService.setPersonaVoice`, `PUT /api/app/parlor/personas/:id/voice`) so a bad name fails at edit time, never mid-session; the persona modal's voice picker is fed by `listVoices()` (`GET /api/app/parlor/voices`), and `manageParlor` can set a voice too. Personas without one get a stable default from a small premade-voice pool keyed by persona id — a fresh cast sounds distinct out of the box. Persona speech is pure output (personas "hear" each other by reading the transcript — a reply is text before it is audio): each completed reply runs through `speechTextFromMarkdown` (code/math/URLs never reach audio, 4000-char cap) into `elevenLabsTTSService.fetchStream(text, { voiceId })`, and MP3 chunks fan out to every connected member tagged with `personaId`/`streamId` through a sequential per-session speech queue (the client plays them in order via MediaSource, Blob fallback). **Barge-in is solo-session only**: real words from the one connected speaker abort the in-flight speech upstream and drop the queue; shared sessions keep it simple (local pause). Guardrails: live capability requires the ElevenLabs key (`GET /api/app/parlor/live/capabilities`; no key = the 🎙️ button never renders), 45-minute session cap, per-user session-join rate limit, 60s utterance cap, bounded audio chunks — all transient in-memory state (live sessions are re-derivable, the Activity-session exception). Nothing new persists beyond the voice columns on an already-covered table (no new privacy surface); STT/TTS usage is logged to the OWNER's DM scope (the host pays for their salon).
- **The invite picker is sourced from the user's Discord friends** (`services/friendService.js`, `user_friends`): you pick a person, never paste a snowflake. Discord does not expose relationships to bots — the *only* surface that can read a friend list is the Embedded App SDK's `getRelationships()` inside the Activity, with the `relationships.read` scope (Social SDK terms, accepted per app in the developer portal). So the **Activity is the collector**: opt-in via `activity.relationships`, it adds the scope to `sdk.commands.authorize()` and POSTs the roster to `POST /api/activity/relationships`, which caches it for the web app that can never read it itself. Requesting the scope without the terms accepted breaks authorize, so the client **falls back to the base scopes** and the sync is fire-and-forget — a friendless picker is never a broken game or a broken parlor. The service legalizes the client payload the usual way (only `type: 1` friends, snowflake ids, no bots, no self, bounded count/lengths), and a re-sync **replaces** the roster (a cache, never a log). Because a self-hosted instance may have no Activity at all, `listInvitable` merges a second source the bot *can* see — members of guilds the user shares with Goobster (membership-gated, cache-first, REST member search only for an explicit query, bounded by guilds scanned and candidates returned) — deduped behind the friends, who keep their badge. `parlorService.listInvitable` (owner-only) subtracts whoever is already seated or holds a pending invite; typing a raw user id still works, so an invite is always possible.
- Privacy: `/forget-me` deletes the whole parlor outright (`parlor_personas` + `parlor_conversations`, cascading notes/tags/links/messages/seats/members/invites) plus the user's footprint in OTHER people's shared parlors (`parlor_members` rows, `parlor_invites` addressed to them, `parlor_messages` they authored) and their cached friend roster **in both directions** (their own list and their appearance in anyone else's — it re-syncs for those users on their next Activity load); `auditUser` counts all of these and `buildUserReport` reports persona/note/discussion/shared-discussion/pending-invite and friend-roster counts. Any new parlor table must hang off one of the two owner-keyed roots (or be added to all three paths).

### The code sandbox (`runCode` tool)
- Goobster can write and run short, resource-limited snippets of Python / Node / Bash for a user and return their output plus any files they produced — the headline use case is **generating diagrams** (Python + matplotlib → a PNG rendered inline in the web app). Service: `services/sandboxService.js`; config: `config/sandboxConfig.js`; tool: `runCode` in `utils/toolsRegistry.js` (picked up by the shared agent loop like every other tool — never a parallel executor path). Full guide: `documentation/code_sandbox.md`.
- **Opt-in and gated, off by default** (`config.sandbox.enabled` / `GOOBSTER_SANDBOX_ENABLED`). When disabled the tool is not registered at all (it never appears in the model's function list). `sandbox.scope` (`web` default, or `everywhere`) decides where it is offered: `web` limits it to the authenticated web app chat (the smallest audience) and it is refused everywhere else; it is never added to the voice tool subset. `toolsRegistry.getDefinitions(names, { isWeb })` performs this filtering, and `chatHandler` passes `isWeb` from the `web:<userId>:<key>` channel-id shape.
- **The trust boundary is the usual one — the model proposes, the service legalizes.** The model only ever supplies a `language` + `code` string; `sandboxService` decides how it runs and never trusts the snippet. Every run gets, regardless of what the code asks for: an **isolation ladder** (bubblewrap read-only-root + private `/tmp` + no-network namespace → `unshare -rn` → rlimits-only best effort, auto-detected once and logged when degrading); **POSIX rlimits** (CPU seconds, virtual memory, file size, process count — a fork-bomb guard); a **hard wall-clock `timeout`** with a Node-side backstop kill; a **scrubbed environment** (no Discord token, no AI keys — only a tiny PATH/HOME/locale allowlist plus a headless-matplotlib nudge); a **private per-run workdir** under `data/sandbox/runs/<id>/` (mode 0700, pruned after `retentionHours`); **byte-capped** stdout/stderr; and **concurrency + per-user rate limits** (in-memory transient state, the allowed exception to the SQLite rule). Every config knob is clamped to a hard ceiling in `sandboxConfig.js`, so a config typo can never remove a guardrail.
- **The Python toolkit**: `config/sandboxPackages.js` is the single source of truth for the curated packages — a catalog of **bundles** (`core`: numpy, scipy, matplotlib, pandas, pillow, sympy, networkx; `astro`: astropy, photutils, specutils, reproject; `imaging`: scikit-image, imageio, h5py — all with ARM64 wheels), each package declaring both its pip name and its import name. `npm run sandbox-python` (`scripts/setup-sandbox-python.js`) installs from that catalog into a managed venv at `data/sandbox/venv`, one pip invocation per bundle so a group that fails to build doesn't cost the others; the sandbox probes the same catalog. Never add a package list anywhere else — extend the catalog. Selection is `--bundles` (one-off) → `sandbox.pythonBundles`/`GOOBSTER_SANDBOX_PYTHON_BUNDLES` → the whole catalog, with `core` always included and unknown names reported instead of silently dropped; `sandbox.extraPythonPackages` (`pip-name` or `pip-name:import_name`) adds packages beyond it, validated against a name pattern so an operator value can never turn into a pip flag. Interpreter resolution is env → `sandbox.pythonCommand` → the managed venv when present → bare `python3` (an explicit setting always wins). The service probes once (via `find_spec`, importing nothing) which catalog modules — the whole catalog plus configured extras, not just the installed bundles, so a hand-rolled venv gets its extras advertised — the interpreter can import; `getDefinitions` appends the honest availability note to the `runCode`/`observatory` descriptions, and a python run failing with `ModuleNotFoundError`/`ImportError` gets the same note in its result so the model's retry targets packages that exist. Deliberately excluded: `astroquery` (network client, and sandbox runs have no network) and the `jwst` calibration pipeline (GB-scale, downloads CRDS reference files). User site-packages stay invisible by design (`PYTHONNOUSERSITE=1`) — the venv is the sanctioned way to grow the toolset. Jest specs: `sandboxPackages`, `sandboxPython`.
- **Generated files ride the `generateImage` path**: EVERY file a run writes — images and non-image files (Markdown, CSV, JSON, …) alike — is sent via `interactionContext.channel.send` (images render inline, the rest arrive as downloadable attachments) and recorded on `interactionContext.generatedFiles`, so the web portal persists them in history and re-serves them through the owner-bound `/api/app/files/:id` route. Errors use `SandboxError` (status + machine-readable code, the `PanelError` contract) and are surfaced to the agent loop as recoverable observations, never thrown out of the tool.
- **Operator-approved sandbox requests** (`services/sandboxRequestService.js`, `sandbox_requests`/`sandbox_packages` tables, buttons routed as `*_sbxreq_<id>` in `interactionCreate`): the model may *propose* two host-level mutations, never perform them. **Package installs** (`requestPythonPackages` tool): a pip dry-run (`--only-binary=:all: --report`, `--isolated`, index pinned to PyPI) resolves the exact hash-pinned transitive set without executing anything; approval installs exactly that stored set (`--require-hashes --no-deps`) into the overlay at `data/sandbox/overlay` (a `pip --target` dir joined to runs via `PYTHONPATH` — the curated venv is never mutated, rollback is one `rm -rf`), budgeted by `sandbox.maxOverlayMb`, recorded hash-pinned in `sandbox_packages` (probed/advertised immediately via `sandboxService.refreshPythonModules`, rebuilt byte-for-byte by `npm run sandbox-python`). Specs are validated against a strict `name`/`name==x.y.z`/`name:import_name` grammar so a request can never smuggle a pip flag/URL/path. **Data fetches** (`observatory` `fetch-data` action): host-side download into the project workspace `data/` dir through `utils/safeFetch` — https-only, no redirects, DNS resolved once with every address required public (loopback/RFC1918/link-local/CGNAT/NAT64-mapped refused) and the connection pinned to the checked address, received-bytes cap (`sandbox.maxFetchMb` ∧ remaining project quota), no overwrites, sanitized basenames. **Approvers are `sandbox.approverUserIds` (operator-level; Manage Server is deliberately NOT sufficient — these mutations are shared by every guild)**, asked by DM with Approve/Deny buttons (12 h TTL, SQLite-persisted); `sandbox.fetchAllowedHosts` grants standing consent per host. Nothing configured = features off (`requestPythonPackages` is not even offered). Requester is DMed the outcome; `/forget-me` deletes request rows and anonymizes package attribution. Jest specs: `safeFetch`, `sandboxRequests`, `sandboxRequestTool`.

### The Observatory (persistent simulation projects, `observatory` tool)
- Persistent, long-running simulation projects layered ON TOP of the code sandbox — the sandbox as a lab bench instead of a scratchpad. Service: `services/observatoryService.js`; config: `config/observatoryConfig.js`; tool: `observatory` in `utils/toolsRegistry.js`; tables: `observatory_projects` / `observatory_jobs`; portal pane: `web/app/observatory.js` + `/api/app/observatory/` routes. Full guide: `documentation/observatory.md`.
- **Opt-in and doubly gated, off by default** (`config.observatory.enabled` / `GOOBSTER_OBSERVATORY_ENABLED`): the tool is not registered unless the Observatory AND the sandbox are both enabled — it grants **persistence, never new execution powers**. `observatory.scope` (`web` default, or `everywhere`) mirrors the sandbox scope rule; never in the voice subset.
- **Projects** are named per-user workspaces at `data/sandbox/projects/<userId>/<slug>/` (mode `0700`, per-user cap, per-project disk quota enforced before every run). A project run keeps its throwaway sandbox workdir as cwd, plus the workspace bind-mounted read-write (bwrap) and exposed as `$GOOBSTER_PROJECT_DIR` — the only writable path beyond the run dir; everything else about a run (isolation ladder, rlimits, scrubbed env, timeout, output caps, concurrency, rate limits) is unchanged sandbox behavior.
- **Background jobs are many small legal runs, not one lawless big one**: `run` with `background: true` detaches into an `observatory_jobs` row whose engine runs the same snippet in segments, each a normal sandbox run holding a concurrency slot honestly. The checkpoint convention (documented, not magic): code loads `$GOOBSTER_PROJECT_DIR/checkpoint.json` when present and rewrites it as it progresses; a segment killed at the timeout wall is resumed only when the checkpoint's mtime advanced, up to the clamped `maxResumes`. Exit 0 completes; non-zero fails; timeout without checkpoint progress is terminal with the reason recorded. Only the first segment counts against the user's sandbox rate limit (resumes are service-initiated and budget-bounded); a busy sandbox defers a segment with backoff instead of failing the job.
- **Restart-safe by SQLite**: job records (code included) persist; a `RUNNING` row with no live in-process handle is reaped to `INTERRUPTED` at first use after a restart, and **checkpointed `INTERRUPTED` jobs auto-resume on startup** (`autoResumeInterrupted`, called from `index.js` after the client is ready — respects the per-user active-job cap, never consumes the timeout-resume budget) so a deploy or crash never silently freezes a long-running simulation; jobs without a checkpoint stay `INTERRUPTED` for a manual `resume`, as do `TIMED_OUT` jobs with budget left. `cancel` kills the live segment's whole process group (the sandbox spawns detached and group-kills for exactly this reason).
- **Render pipeline**: numbered frames in `$GOOBSTER_PROJECT_DIR/frames/` (`frame_0001.png`, …) are stitched into `renders/render_<n>.mp4` via system ffmpeg automatically when a job completes, or on demand (`render`, optional fps, `maxRenderFrames` cap). Missing ffmpeg degrades to a clear message, never a crash.
- **Notifications ride the existing follow-up machinery**: a finished job files a `followups` row due NOW in the user's DM scope (DM channel resolved through the client), delivered and phrased by heartbeatService's minute loop. No connected client = no notification, never an error — the job record and portal pane remain the status surface.
- **The dashboard artifact** (`services/observatoryDashboard.js`): the final step of every run/job regenerates a self-contained HTML results dashboard — job timeline, inline render video + image gallery (base64, extension-checked, size-capped), checkpoint, file table. Authored ONLY by deterministic server code and stored OUTSIDE the snippet-writable workspace (`data/sandbox/dashboards/<userId>/<slug>.html`) with everything escaped + a strict CSP, so a run can never smuggle markup into a trusted page. Owner view is live (`GET /api/app/observatory/projects/:slug/dashboard`, regenerated when stale) with auth-probed control buttons (per-job cancel/resume, render, refresh) that call the normal routes; one revocable read-only share link per project (`observatory_share_links`, unguessable-token capability, `/app/observatory/share/<token>`, regenerated on view) stays inert for viewers because the owner-session probe fails. The `dashboard` tool action attaches the artifact in chat. Share links are covered by the transparency report, `/forget-me`, and `auditUser`.
- Privacy: projects and jobs are in `/what-do-you-know-about-me`, `/forget-me` (rows + the whole on-disk workspace tree, live jobs cancelled first), and `auditUser` (both tables plus leftover workspace dirs). Every numeric knob in `observatoryConfig.js` is clamped floor/ceiling like the sandbox's. Jest specs: `observatoryConfig`, `observatoryService`, `toolsRegistryObservatory`.

### The Goobster Tavern + Adventure Mode ("Tavern Alpha")
- A persistent social hub + lightweight tabletop RPG (`commands/tavern/`: `/tavern`, `/character`, `/adventure`, `/roll`; services under `services/tavern/`). Full player/author guide: `documentation/tavern_adventure_mode.md`.
- **Campaigns are YAML directories, not code** (`services/tavern/questLoader.js`): built-ins in `campaigns/<quest-id>/` (`quest.yaml` + `scenes/*.yaml` + `endings.yaml`), custom/generated ones in `data/tavern/campaigns/` (gitignored; same id overrides a built-in — the supported "alter a module" path; `/tavern reload-quests` hot-reloads). Everything is validated on load with file-path errors; invalid custom campaigns are warned and skipped (never a crash), invalid built-ins throw and are covered by tests. Effects are a **closed vocabulary** (`clock`, `damage`, `heal`, `item`, `spark`, `flag`, `goto`, `end`) so the engine stays deterministic no matter who wrote the YAML.
- **Structured state is separate from prose** (the fog-bank rule): deterministic records live in `tavern_characters` and `tavern_adventures.state` JSON (clocks, flags, used options, spotlight order, big-move usage, last check for Spark rerolls); narrative text lives in `tavern_adventure_log` (scene beats, actions, checks, and the automatic RECAP row written on completion).
- Rules (alpha): four stats (Might/Finesse/Wits/Heart, +0..+3, 6 points at creation), checks are d20 + stat vs DC bands (10/13/16/19), six Callings each with a once-per-adventure big move (auto-success on the next check), one complication per character, Spark (0-5) rerolls a failed check (the first attempt's costs stand), health floors at 1 ("staggered" + danger tick — no permadeath), completion grants a milestone (`/character advance` raises a stat, max +3), full heal, +1 Spark, and any ending trophy.
- `services/tavern/adventureService.js` is the engine: party lifecycle (one open adventure per channel, one per user per guild, join/leave/abandon are safety tools that never punish), option checks and travel options, freeform actions (`/adventure act`) with deterministic keyword stat inference, clock `onFull` triggers, and recap assembly. The RNG is constructor-injectable (like `GamblingService`) so game logic is deterministic under test.
- **AI is flavor, never mechanics** (`services/tavern/narrator.js`): optional stat/DC interpretation for freeform actions (clamped to real stats/bands), outcome narration, and recap polish — all with timeouts and null fallbacks to pre-authored campaign prose + keyword inference. Fully playable with no AI provider. AI calls carry `usageContext`.
- Buttons (`join`/`begin`/scene options/Spark reroll, customId `<action>_tavern_<id>[-<optionKey>]`, routed in `events/interactionCreate.js` to `services/tavern/interactionHandler.js`) are restart-safe because all state is in SQLite; option keys are validated slug-only (no underscores) to survive the customId split.
- Privacy: `/forget-me` deletes tavern characters + party seats + NPC relationships + Guest Rooms, anonymizes shared adventure records (`createdBy`, log attribution), scrubs the user's id from adventure-state JSON, and runs a review pass over adventure-log prose **and shared lore** using the user's character names (collected into `knownNames` before deletion); all covered by `auditUser` and `tests/tavernPrivacy.test.js`.
- **Phase 2 - the world remembers**: per-member NPC relationship scores (`tavern_npc_relationships`, clamped -5..+5, moved by the `npc` YAML effect - travel/ending options may carry an `effects` block too), Guest Rooms (`tavern_rooms`, `/tavern room|room-edit`), the shared lore record (`tavern_lore`, written by `world:` entries on endings, browsed via `/world map|lore`, capped 200/guild), and campaign chapters (`requires:` in quest.yaml gates a quest until the required one is COMPLETED in the guild - built-in example: `signal-in-the-salt`).
- **Goobster plays too** (`services/tavern/botAdventurer.js`, mirroring the casino `botPlayer` rules): `/adventure invite-goobster` (or the `tavernParty` tool) seats him with a lazily-created per-guild Oddity character keyed on his **real bot account id**. Turn triggers are fire-and-forget calls from the button handler / `/adventure act` / the tools; he acts only when the spotlight rotation reaches him, after an unref'd think delay. **The model decides, deterministic code legalizes**: AI ONLY-JSON decision → `legalize` (listed check option or ≤300-char freeform; travel/ending options are filtered out - he follows, never leads) → `_fallback` (best-stat option) only when no usable answer. His failures never show players a Spark-reroll button.
- **Tavern tools** (`utils/toolsRegistry.js`): `tavernInfo`, `tavernParty` (create/join/begin/leave/invite-bot), `tavernAct` (freeform for the requesting user; posts outcome + scene to the channel), `tavernRecap`, `rollDice`. `tavernInfo` + `rollDice` are in the voice subset; the play tools are in `TEXT_CHANNEL_TOOL_NAMES` (they post into the transcript channel). All friendly errors return text, never throw.
- **Generated assets live in `data/`** (`services/tavern/assetService.js`): scene art at `data/tavern/assets/scenes/<quest>/<scene>.png` - generated once via `/tavern generate-art` (Manage Server, OpenAI images), then served from disk forever; scene embeds attach art when the file exists (in-place scene updates pass `attachments: []` so re-attached art doesn't stack). No key → text-only, never an error.
- **Combat** (Phase 3): scenes with an `encounter:` block arm deterministic combat state in `adventure.state.combat` on entry (fresh per entry). Enemies have health, a defense DC, flat damage, and cycling **telegraphed intents**; `attack` (buttons `atk_tavern_*`, `/adventure attack`, the `tavernAttack` tool) rolls d20 + best-of-Might/Finesse (or an override) vs defense - hits deal 2 (+1 nat 20), misses can be Spark-rerolled. Every party action (checks, freeform, items, attacks) advances the round; after party-size actions each living enemy executes its telegraphed intent against the last actor, then telegraphs the next (`_tickCombat`). Defeats fire `onDefeat` effects, the last kill fires `onVictory`; social/trick options stay live so combat is always bypassable. No party wipe - the danger clock remains the fail-state. Showcase campaign: `dungeon-tenant-rights`.
- **Inventory** (Phase 3): `/character inventory view|use|give|drop` (item autocomplete from the pack). Consumables are defined per campaign (`quest.yaml items:` → `use: {heal?, spark?, text?}`) and resolved at use time from the ACTIVE adventure's quest; using one is an action (draws the combat round). `characterService.removeItem`/`transferItem` are the mutation points.
- **The campaign forge** (`services/tavern/campaignForge.js`) - Goobster writes campaign YAML himself, always through the same trust boundary: **the model proposes JSON, deterministic code validates and writes files**. `/tavern forge` (Manage Server) generates a whole new campaign into `data/tavern/campaigns/` (validated via `validateQuest`, one repair round, id-collision suffixing, never overwrites). `/adventure twist` / the `tavernTwist` tool (party member, once per adventure) forks the RUNNING campaign into a hidden override (`<canonical>--twist-<adventureId>`, `hidden: true`, `canonicalId` set): 1-3 new scenes merged onto a full copy, `checkTiesBack` proves by graph reachability that every new branch leads back to ORIGINAL scenes/endings (no new endings allowed), then the live adventure is re-pointed via `adventureService.applyTwist`. Hidden quests never appear on boards/autocomplete (`getVisibleQuests`), can't seed new parties, and their completions satisfy `requires:` gates on the canonical id. `GOOBSTER_TAVERN_CAMPAIGNS_DIR` overrides the custom dir for tests.

Public-repo reads work keyless; a fine-grained PAT raises rate limits and unlocks code search and private repos. File fetches are size-capped (100KB) so a single file can never blow up a prompt.

Watched repos **double as the per-guild allowlist** for the GitHub chat tools (`searchGithubCode`, `readGithubFile`) and `/agent launch` — nothing reads from or launches against a repo an admin hasn't watched. Webhook events become embeds in the watch channel; CI events post failures only (green runs would drown the channel).

Status changes, the final summary, and PR links post back to the launch channel.

Receivers ACK 202 fast and process async.
- Guardrails: `Manage Server` gates watches and everything that spends compute or changes state (`/agent launch|followup|cancel`); every write-side action is recorded in the `integration_audit` ledger (`services/integrationAudit.js`, wrapped like `usageTracker.log` — auditing never breaks the action). `/github` and `/agent` invocations are counted in `command_log`.

### Voice conversations
- `/voicechat` runs live voice sessions with two engines behind one manager (`services/voice/voiceSessionService.js`, one session per guild):
  - **realtime** (default): GPT-Voice-style low latency. Per-user Opus audio streams into ElevenLabs **Scribe v2 Realtime** (`services/voice/scribeRealtimeService.js`, 16kHz mono via `pcmUtils.stereo48kToMono16k`) *while the user is talking*; LLM replies stream token-by-token (`opts.onDelta`) into the ElevenLabs **multi-context TTS WebSocket** (`services/voice/multiContextTTSService.js`), so playback starts on the first sentence. True **barge-in**: a wordful speaker starting to talk (or words detected on a previously-noisy mic) closes the TTS context server-side, stops playback instantly, and the interrupted reply is recorded in history as `[interrupted by a user mid-reply]`. The coordinator lives in `services/voice/realtimeVoiceEngine.js`. Requires only an ElevenLabs key; per-segment fallback to OpenAI batch STT when the realtime API errors and a key is available. Protocol note (verified live): the multi-stream API only emits `isFinal` after `close_context`, so `finish()` sends `flush` + `close_context` together — a closing context still delivers its remaining flushed audio.
  - **classic**: the original batch pipeline — silence-based end-of-utterance capture, batch transcription via `services/transcriptionService.js` (OpenAI `gpt-4o-mini-transcribe`), full reply generation, then ElevenLabs HTTP streaming TTS. Requires OpenAI (STT) and ElevenLabs (TTS) keys.
- Cost/noise guardrails shared by both engines: an RMS energy gate keeps open-mic noise away from paid STT entirely (the realtime engine buffers locally and only opens an STT connection once a chunk crosses the gate), and per-speaker `emptyStreak` tracking stops noisy mics from blocking turn-taking or triggering barge-in.
- Shared turn logic (polite-mode gate, tool interaction context, the voice hooks for the agent loop) lives in `services/voice/voiceTurnShared.js` — never duplicate it in an engine.
- **Notification cues** (`services/voice/notificationSounds.js`): both engines play a soft rising chime when a turn is accepted and reply generation begins (after the polite-mode gate — silent turns must stay fully silent), `createVoiceToolRunner` plays a distinct double-blip once per tool round, and a low descending error cue plays on failure — once per round when a tool call errors, and when a turn dies outright (LLM or TTS failure; both engines' `_respondToTurn` catch, cue, and rethrow so listeners can tell an error from a snub). Cues are synthesized PCM (no audio assets, no cloud API — same philosophy as the Activity's WebAudio sounds), fire-and-forget, and never throw: playback briefly subscribes its own player and then restores whichever player held the connection (session TTS players pause while unsubscribed, so in-flight speech resumes).
- **Speech playback borrows the guild voice connection and must hand it back** (`services/voice/voicePlaybackCoordinator.js`): a guild has one voice connection and it plays one AudioPlayer at a time, so any speech that subscribes its own player displaces whatever was playing (usually `/play` music, which then sits in AutoPaused). Both TTS engines capture the displaced player and restore it when speech ends: the HTTP TTS service restores in a `finally` around playback (covers `/speak`, classic `/voicechat`, the AI DJ, and casino table talk), and the multi-context streaming TTS restores on `finish()`/`abort()`/`destroy()` (realtime `/voicechat`, including barge-in). Restoration always yields to a newer claimant of the subscription. `/voicechat stop` hands a connection that active music is sharing back to the music player instead of destroying it, and `MusicService.resume()` recovers from AutoPaused by re-subscribing its own player. Never subscribe a long-lived player to a connection without going through this borrow/restore contract.
- **Spoken text never contains URLs** (`services/voice/speechText.js`): `stripUrlsForSpeech` sanitizes whole replies inside `elevenLabsTTSService.textToSpeech` (covering voice sessions, `/speak`, the AI DJ, and casino table talk; URL-only text skips synthesis entirely), and the realtime engine routes streamed deltas through `createStreamingUrlStripper`, which holds back the trailing unfinished word so URLs split across LLM deltas are still caught. Conversation history and the text-channel transcript keep the full reply, links included — only the audio path is stripped.
- **Voice tool calling**: voice turns run the same bounded agent loop as text chat (`runAgentLoop` from `utils/chat/agentOrchestrator.js`, `VOICE_MAX_TOOL_ROUNDS` = 3 sequential tool rounds plus a forced finalization round, duplicate-call caching, tool errors as recoverable observations), so users can trigger server functions by speaking and always hear an answer. Voice-specific behavior plugs in via hooks: `createVoiceToolRunner` (cues + captured `reply()` output) and `shouldAbort` (barge-in stops the loop without finalization). Available by voice: web search (`performSearch`, plus native `opts.webSearch` on OpenAI/Gemini), `rememberFact`/`forgetFact`, `setNickname`, the economy tools (`checkPoints`, `gamblePoints`, `stockQuote`, `tradeStock`, `checkPortfolio`), and (only when the session has a transcript text channel) `generateImage` and `scheduleFollowUp`. The subset is defined once in `voiceTurnShared.js` (`VOICE_TOOL_NAMES`/`TEXT_CHANNEL_TOOL_NAMES`) and exposed via `toolsRegistry.getDefinitions(names)`.
- Tools receive a synthetic interaction context built by `_buildToolContext`: guild/channel/client plus the turn's most recent speaker as `user`/`member`; `reply()`/`editReply()` output from wrapped commands is captured and appended to the tool result so the model voices real outcomes (e.g. permission denials). `playTrack` is deliberately excluded — music playback would destroy the session's own voice connection — as are `speakMessage`/`echoMessage` (redundant when every reply is already spoken).

### Goobster Plays Pokémon (GBA agent harness — Phase 0)
- Design doc: `documentation/goobster_plays_pokemon.md`. Architecture rule: **the laptop is the player, the Pi is the broadcaster** — the emulator, the MCP server, and (later) the AI handler run on a helper machine; Goobster only receives events/screenshots and forwards advice, degrading to "run paused" when the helper is offline (screen-companion pattern).
- `clients/gba-mcp/` is a **zero-dependency** companion tool (like `clients/screen-companion`): `goobster-gba.lua` runs inside mGBA (0.10+ scripting API) and serves a percent-encoded line protocol on loopback TCP (`127.0.0.1:5771`); `server.js` is a from-scratch newline-delimited JSON-RPC MCP stdio server (initialize / tools/list / tools/call / ping) exposing `get_screen` (PNG, nearest-neighbor upscaled via the zero-dep codec in `lib/png.js`), `press_buttons` (sequences + `"B+RIGHT"` combos), `wait`, `save_state`/`load_state`, `get_status`, and `read_memory`.
- Trust boundary as everywhere else (**model proposes, deterministic code legalizes**): every tool input is validated/clamped in `lib/tools.js` and bad input returns a corrective tool error, never reaches the emulator. **Vision-first rule**: `read_memory` exists for loop-detector ground truth but is hidden unless the operator passes `--allow-memory`.
- The bridge client (`lib/mgbaClient.js`) connects lazily, reconnects after emulator restarts, and sizes timeouts from the frame budget; frame-consuming verbs (press/wait) run one at a time inside the Lua script's frame callback. Both processes must share a filesystem (screenshot hand-off is a temp file).
- **No ROMs ship.** `clients/gba-mcp/test-rom/` builds a homebrew test ROM (`gcc-arm-none-eabi`) so the harness is exercisable legally; `mgba-headless-videobuffer.patch` fixes a dev-build crash (`emu:screenshot()` with no video buffer attached) for headless testing. Jest spec: `tests/gbaMcp.test.js` (codec, legalization, PNG, MCP framing, bridge client against a fake bridge).
- **Phase 1 — the broadcast pipe** (`services/gbaRunService.js`, `web/gbaRunApi.js`, `commands/utility/gbarun.js`): opt-in via `config.gbaRun.enabled` (public server gains `POST /api/gba-run/pair` + `WS /api/gba-run/ws`). Pairing is **guild-scoped and Manage Server gated** — `/gbarun link [channel]` binds ONE harness per guild to ONE broadcast channel (checked for the bot's View/Send/Attach perms) and issues a single-use code (screen-vision pattern: SHA-256 token hash in `gba_run_clients`, redeem throttling, newest connection wins, re-pair revokes the old token).
- The harness protocol is hello/status/post: `post` messages (text and/or base64 PNG) are **queued per guild and rate-limited server-side** (3s minimum interval, bounded queue — overflow is acked as failed, never buffered forever), delivered via `channel.send` with every failure acked back to the driver rather than thrown. `status` carries the game title for `/gbarun status`.
- `clients/gba-mcp/run-driver.js` (zero-dep, Node 22+ built-in WebSocket/fetch) executes **playbooks**: JSON step scripts (`press`/`wait`/`post`/`save`/`load`/`note`) validated up front with step-position errors by `lib/playbook.js` (questLoader style — a typo fails before the run starts). Pairing persists in `goobster-gba-run.json` next to the driver (gitignored); `--dry-run` rehearses without Goobster. Delivery is best-effort: a dead broadcast connection skips posts and keeps the run going. Jest spec: `tests/gbaRunService.test.js`.
- **Phase 2 — the autonomous player** (`clients/gba-mcp/agent.js` + `lib/gameAgent.js`): a perceive-think-act loop where the vision model answers ONLY JSON and `lib/agentBrain.js` legalizes it (button vocabulary + `WAIT`, 8-action cap, unusable answers degrade to watching — never crash, never press garbage; N consecutive brain failures end the run with a post). Providers live in `lib/visionModel.js` (zero-dep fetch, deliberately NOT `services/aiService.js`): Ollama multimodal (default `qwen2.5vl:7b`) and OpenAI Responses (`--provider openai`) — the cloud-provider parity rule does not apply to this laptop-side tool.
- **Anti-stuck ladder v1** (`lib/stuckDetector.js`): frames compare as a 15x10 grid of average-color cells (≤2 changed cells = "same screen", so idle animations don't mask stuckness) escalating warn → push → checkpoint reload; the agent saves a watchdog state every N turns (slot 9) plus one at run start so a reset always has a target. Broadcasts ride the Phase 1 pipe: milestones post immediately (the prompt forbids repeat milestones), heartbeats every `--post-every` turns, and stuck-resets announce themselves. Jest spec: `tests/gbaAgent.test.js` (brain legalization, stuck escalation, Ollama provider against a fake HTTP server, full loop against a scripted brain + fake bridge writing real PNGs).
- **Deterministic feedback beats prompt hope**: actions rejected by legalization are reported back in the NEXT prompt (one-shot), and a turn whose presses changed nothing gets its history line annotated `[the screen did NOT change after this]` — the model always sees consequences, never silence. The system prompt teaches menu-cursor mechanics (D-pad moves the highlight, A confirms what is highlighted NOW, SELECT ≠ "select the option"), overworld tile movement (turn-then-step, wall bumps, walk-into doors), and battle-menu play; per-game notes go in `--hints`/`--hints-file` (ships `hints/pokemon-firered.txt`, which includes the FireRed early-game critical path — the "mostly-hardcoded goal graph" in hint form), never hardcoded into the agent.
- **Phase 2.x — RAM ground truth** (`clients/gba-mcp/lib/gameState.js`, agent `--allow-memory`/`GOOBSTER_GBA_ALLOW_MEMORY=1`): the design-rule memory opt-in, limited to the sanctioned set — player coords, map id, in-battle flag. `GameStateReader` follows the DMA-shifted save-block pointer per read (pret-decomp addresses keyed by cartridge code: BPRE/BPGE/BPEE) and returns null on unknown games, failed reads, or implausible values (the agent plays that turn vision-only — never an error). The agent turns reads into a deterministic `GROUND TRUTH` prompt block: position/map, movement since last turn in button vocabulary ("you moved 2 tiles RIGHT"), wall-bump callouts when D-pad presses moved nothing, battle start/end transitions, same-tile streaks, and `TileMemory` explored-map hints (bounded per map/run; never-visited adjacent directions drive systematic exploration). A checkpoint reload clears the movement comparison (the reload teleported the player). `--reasoning minimal|low|medium|high` (OpenAI provider only) turns on Responses-API reasoning per decision. Jest spec: `tests/gbaGameState.test.js`.
- **Phase 2.x — sync mode** (bridge `hold`/`release`, agent default-on, `--no-sync` opts out): the game freezes while the model thinks. `goobster-gba.lua` implements `hold` by trapping the emulation thread in its frame callback and polling client sockets manually (`sock:poll()` — blocked callbacks get no automatic event dispatch); instant verbs still work against the frozen state, and the freeze ends on `release`, implicitly on the next `press`/`wait`, on timeout (`timeout=` param, default 120s / cap 300s), or when the last client disconnects — a dead agent can never leave mGBA frozen. Agent side (`_holdIfSync`/`_releaseIfHeld`): hold before the turn's screenshot (screenshot + RAM reads + deliberation describe one instant), `_executeActions` marks the hold consumed, `runTurn` releases in a `finally` on every non-press exit; sync support is probed by the first hold of the run and a failure (older Lua script) falls back to the fresh-frame guard. While held, the guard recapture is skipped (a frozen screen cannot drift). The stuck-reset path re-renders (2-frame wait) and recaptures after a checkpoint reload so the model sees the restored screen.
- **Phase 2.x — the fresh-frame guard** (`gameAgent.js` `runTurn`, the fallback when sync mode is off or unsupported): mGBA cannot be paused from the scripting API, so decisions execute seconds after their screenshot. Right before executing, the agent recaptures and compares frames (`stuckDetector.frameSignature`/`changedCells`; `GRID_CELLS` exported): drift ≥ half the grid with presses queued → the presses are HELD (`stats.staleSkips`), the history line is annotated, and a one-shot `staleNotice` tells the model to re-decide from the fresh screen; a wait-only decision whose screen already moved past the still tolerance is skipped (`stats.waitSkips`) — never burn real time waiting for something that finished during thinking. The system prompt teaches decision latency and the corrected dialog rule (A is always safe in dialog — fast-forwards then advances; the blinking arrow is not always shown, `hints/pokemon-firered.txt` matches). Ground truth adds an A-B-A-B position-trail ping-pong callout (trail cleared on checkpoint reload).
- **Phase 2.x — the experience book** (`clients/gba-mcp/lib/experience.js`): cross-session learning, on by default (`--no-learn` opts out, `--experience-file` relocates), persisted per game code in `goobster-gba-experience.json` (gitignored next to the agent, like the pairing file). Two kinds of learning, both behind the usual trust boundary: (1) **model-written lessons** via an optional `"learn"` decision field — deterministic code trims (200 chars), rejects trivia, dedupes by normalized text (repeats reinforce the existing lesson's `seen` count), caps storage at 60 per game evicting least-reinforced-oldest first, and renders the most recent 40 into the system prompt; (2) **deterministic behavior memory** the harness collects itself — per-tile wall bumps recorded only when exactly one direction was pressed and RAM says the player didn't move, reported as known-blocked once seen twice (`bumpReportThreshold`); the explored `TileMemory` (now serialized across sessions via `toJSON`/`fromJSON`, caps re-applied on load); and achieved milestones (deduped, injected as "PROGRESS ALREADY MADE" so old wins are never re-announced). Lesson/milestone writes rebuild the system prompt immediately (learning applies next turn, not next session) and trigger a save; saves also ride the watchdog-checkpoint cadence and run end (atomic temp-file + rename; corrupt/unwritable files log and degrade to in-memory). Jest spec: `tests/gbaExperience.test.js`.
- **Phase 3 — the show** (`gbaRunService` + `events/messageCreate.js` + agent): the **advice inbox** consumes non-mention messages in the bound channel while a harness is CONNECTED (`maybeCaptureAdvice`, placed AFTER explicit-address handling so mentions still reach chat; 📨 ack; author display name + text forwarded, nothing stored). The **live status embed** is one persistent message per guild (`gba_run_clients.statusMessageId`, column-migrated) edited in place from coalesced per-turn `run` frames (10s min interval), flipping to paused/ended on disconnect via a run snapshot that outlives the connection. **Milestones** (`milestone` frames) post as gold embeds AND insert into `gba_run_milestones` — shown by `/gbarun status`, scrubbed by the `/forget-me` review pass (model text may credit users by name), and reserved as the Phase 4 bet-settlement source.

## Core Features

### Chat Interaction
- Natural language processing with multi-turn conversation memory (stored in SQLite)
- Context-aware responses with automatic conversation summarization
- Command-based and @mention interactions, intent-checked replies to his own messages, plus optional dynamic responses
- Message reactions: regenerate, pin, branch, deep dive, summarize

### Music & Audio
- Track downloads via SpotDL/yt-dlp to local storage
- `/play url:<...>` plays straight from a URL: YouTube videos/playlists (yt-dlp audio extraction) and Spotify tracks/playlists/albums (spotdl). The bot joins the caller's voice channel immediately, reuses MP3s already in `data/music` (spotdl skip-detection / yt-dlp `--no-overwrites`), and starts playback on the first resolved track while the rest of a playlist downloads in the background and queues progressively (`services/urlPlayService.js` routes URLs; `services/ytdlp/ytdlpService.js` mirrors the spotdl service's CLI discovery, with a `ytdlp.path` config override)
- Playlists persisted as JSON on disk, playback queue, AI DJ
- All generated audio via ElevenLabs (optional): TTS, mood music (Music API), and ambient sound loops (Sound Effects API)

### Meme Mode
Meme mode allows users to receive responses with added meme flair and internet culture references.

#### Usage
- `/mememode toggle <true/false>` - Enable or disable meme mode
- `/mememode status` - Check current meme mode status

#### Technical Implementation
- User preferences stored in the `UserPreferences` table (SQLite)
- In-memory caching for 5 minutes
- Affects all AI-generated responses: chat, jokes, poems, search

### Economy & Games
- Named per-guild point currency with wallets, ledger, daily claims, transfers, and leaderboards
- Gambling: coin flips, d20 showdowns, and 5-card poker against the dealer (even money, push on ties)
- Stock trading game: live quotes (keyless Yahoo endpoints, SQLite-cached), buy/sell with points (1 point = $1), tracked cost basis and trade history, portfolio check-ins with P/L, and historical price charts
- The Jimbucks Exchange (opt-in per guild): margin accounts with leverage, interest, margin calls, and forced liquidation; short selling with borrow fees; options long and written on simulated Black-Scholes chains — same-day index contracts behind a Goblin Mode opt-in, covered/naked writes with real margin requirements, and multi-leg spreads with pre-trade receipts; isolated-margin perpetual futures with funding and liquidation; limit/stop/stop-limit/trailing-stop resting orders; binary event contracts settled from the real price; real dividends and splits applied from the feed
- Group play: a per-member opt-in registry with an override-all default (everyone with a wallet is in unless they opt out, and an opt-out always wins) feeding the Daily Ballistic Goblin Wheel — two spins pick the strike distance and the wallet percentage, then the exchange deploys every participant into the chosen call, on demand or every weekday at the open
- Auditing is a first-class feature, not a debug tool: per-account audits with live greeks and liquidation levels, a server-wide market dashboard, an equity leaderboard, the engine's "why" log, and integrity checks that prove the books add up — all readable by Goobster about any member
- Fully operable via slash commands, text chat tools, and live voice sessions

### System Monitoring
- `/systemstatus` reports CPU load, temperature and throttle state (Raspberry Pi), memory, disk, database size, and gateway latency
- Rotating file logs under `logs/` via the shared winston logger (`utils/logger.js`)

### Local management panel (Raspberry Pi touchscreen)
- A touch-optimized web console (800×400 landscape) for **managing the bot**, not chatting with it: browse the guilds Goobster is in, then per guild send exact bot messages, generate AI-drafted messages (private instruction → editable preview → explicit post; the instruction is never posted or persisted), start/stop live voice conversations, control music playback, and manage settings.
- The Settings tab mirrors every per-guild slash-command setting: proactive mode, dynamic responses, reply detection, search approval, thread preference, AI provider/model/reasoning overrides, the Thoughtful Mode preset, personality directive, bot nickname (DB + best-effort Discord nickname), memory retention (purges immediately like `/privacy retention`), channel memory exclusions (excluding purges stored memories **and** activity counters, like `/privacy exclude`), and forget-all-memories — plus the global ElevenLabs TTS voice (mirrors `/setvoice`: persists to `config.json` and updates the live service). API: `GET`/`PATCH /api/guilds/:id/settings` (partial updates, each key validated like its slash command), `POST .../memory/exclusions`, `POST .../memory/forget`, `POST /api/settings/tts-voice`.
- Architecture: `web/server.js` starts two listeners — the unchanged `/health` server (all interfaces, `PORT`/3000) and the panel server bound to **127.0.0.1 only** (default port 3400; `config.json` `panel: { enabled, port }` or `GOOBSTER_PANEL_PORT`). A Host/Origin guard rejects non-loopback requests. The static client (`web/public/`, no framework, ES modules) and thin routes (`web/panelApi.js`) sit over `services/panelService.js`, which validates all input, resolves live guild/channel objects from the Discord client, and checks the bot's own `ViewChannel`/`SendMessages`/`Connect`/`Speak` permissions before every action. Slash-command interactions are **never** fabricated.
- Errors use `PanelError` (HTTP status + machine-readable code); confirmation-required conflicts return 409 with `requiresConfirmation: true` (moving music between guilds, starting voice chat over active music). Music keeps its single player/queue model: the panel warns and requires confirmation before moving Goobster to another guild, and a live voice-chat session in a guild blocks music there.
- Draft generation reuses the guild's personality (`utils/memeMode.getPromptWithGuildPersonality`), per-guild AI overrides, recent channel messages, and memory recall, with `usageContext: { guildId, userId: null }`.

### Web app (browser chat + memory dashboard + the Parlor)
- Discord-authenticated browser interface at `/app` on the public server (opt-in, served through the same tunnel as the Activity)
- Full LLM chat through the same pipeline as Discord chat: shared DM-scope memory and facts, streaming token-by-token, full Markdown with syntax-highlighted code, LaTeX math (KaTeX served locally), generated images inline, no Discord message-length limits
- The modern chat-app suite: multiple conversations with auto-generated titles (rename/delete/search), Stop generating, Regenerate, edit & resend, image attachments for vision (upload or paste, persisted so they survive reloads) plus text/document/PDF attachments rendered as collapsible chips, copy buttons on messages and code blocks, Markdown export, light/dark theme, a mobile drawer layout, and a Thoughtful Mode toggle shared with `/thoughtfulmode`
- Tool-use transparency: while a reply is being generated, per-tool activity chips stream into the chat ("Searching the web…", "Running code…", ✓/⚠ on completion) - the orchestrator's `onToolEvent` hook flows through the pseudo-interaction into SSE `tool` events
- Full-text search: the sidebar box filters titles instantly and (debounced) searches every message's content server-side, with snippet results that deep-link to the matching message (scroll + highlight)
- Full AI control from the header: provider/model/reasoning-effort settings (shared with `/aisettings`, so Discord DMs follow along), per-user custom instructions (stored on `UserPreferences.custom_instructions`, applied on every chat surface, also editable via `/instructions` in Discord), and an incognito mode whose conversations are never written to history or memory
- Personal integrations (Notion, GitHub): connect your own accounts in the Integrations dialog and chat answers can search your Notion workspace or your GitHub repositories; status and disconnect also available from Discord via `/integrations`
- Mini-apps: ask for something visual or playable and the reply's `html` code block runs live in the chat as a sandboxed interactive app (Preview/Code tabs, restart, fullscreen, download) - the differentiating "Goobster builds you a little tool" feature
- Voice: dictate messages with the composer mic (speech-to-text) and have any reply read aloud in the bot's configured ElevenLabs voice - both degrade away cleanly when no key is configured
- Branching: editing an earlier message can fork the conversation instead of rewriting it - the original stays fully intact and both branches live in the sidebar with lineage badges
- Sharing: a revocable read-only link per conversation that anyone can open without signing in - text only, never other conversations, dead the moment it's revoked
- Scheduled tasks: view, create, pause, and cancel recurring agent prompts and one-shot reminders from the Tasks pane (delivered to your Discord DMs; same rows as `/automation`)
- Personal usage dashboard: your own AI calls and token volume with a daily chart and per-model/per-operation breakdowns
- Memory retention: set an auto-delete window for your DM-scope memories right from the Memory dashboard (mirrors `/privacy retention`, which now works in DMs too)
- Installable PWA (manifest + service worker + icons) with an accessibility pass: focus-managed dialogs, keyboard navigation, aria labels, and reduced-motion support
- Memory dashboard: per-scope transparency report, facts and memories with individual delete controls, and an interactive knowledge-graph visualization with the internal monologue's recent thoughts (Manage Server)
- The Parlor: a multi-persona AI workspace - create personas with distinct charters, seed their private tag-first knowledge workspaces (notes connected through shared tags, semantic search, interactive graph), and hold discussions with up to 4 personas at once where every reply is grounded in that persona's own notes (traceable grounding chips) and new knowledge is extracted back into the workspace as you talk

### Retired Features
The original adventure mode (party/story system) and mystery heroes mode were retired to keep the bot lean on low-power hardware; their commands, services, and database tables were removed. The Goobster Tavern + Adventure Mode is its designed-from-scratch successor: YAML-driven campaigns, a deterministic engine, and AI used only for flavor (see the Tavern section above).

## Development Standards

### Code Organization
- Modular architecture: commands in `commands/<category>/`, business logic in `services/`, shared helpers in `utils/`, database in `db/`
- The chat pipeline lives in `utils/chatHandler.js` (orchestration only) plus focused modules under `utils/chat/`: `chatDb` (rows/tracking/diagnostics), `chatContext` (context window + summaries), `agentOrchestrator` (bounded tool-calling loop + tool-result continuity), `searchFlow` (legacy search approval + response directives), `reactions`, `responder` (chunked delivery), `threadManager`, `prompts`. New chat features belong in the matching module, not in the orchestrator.
- Clear separation of concerns
- Consistent file structure
- Proper error handling — commands must always answer the interaction, even on failure
- **State that must survive a restart lives in SQLite, not process memory.** Examples: heartbeat mood/cooldowns (`heartbeat_state`), pending search approvals (`pending_search_requests`), search dedup (`pending_searches`). In-memory Maps are only acceptable for transient, re-derivable state.
- Errors re-thrown from catch blocks must attach the original error as `cause` (`throw new Error(msg, { cause: error })`).

### Documentation
- Clear and concise comments (explain intent, not mechanics)
- JSDoc for functions and classes
- README files for major components
- Keep this document authoritative and current

### Testing
- Unit tests for core functionality (Jest). Specs live in `tests/*.test.js`; DB-backed specs point `GOOBSTER_DB_PATH` at a throwaway file (see `tests/privacyService.test.js`)
- Smoke test: every module must `require()` cleanly with an empty/minimal config — enforced by `npm run smoke` (`scripts/smoke-require.js`)
- Lint: `npm run lint` (ESLint flat config in `eslint.config.js`) must pass with zero errors
- CI (`.github/workflows/ci.yml`) runs lint + smoke + Jest on every push/PR
- Integration tests for key features

### Security
- Input validation at system boundaries
- Rate limiting
- Secure API key handling (config.json and .env are gitignored)
- Permission management (admin-only commands check permissions)

### Performance (Raspberry Pi constraints)
- Target < 500MB RSS at idle
- Prefer synchronous SQLite (better-sqlite3) over network round trips
- In-memory caches with TTL for hot settings (guild settings, meme mode)
- Avoid architecture-specific binaries; native modules must build or ship prebuilts for ARM64
- Slash command registration is skipped when unchanged (hash cache) to avoid Discord rate limits on frequent reboots
